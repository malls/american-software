## Findings (5; 1 worth a ruling, 4 low/trivia)

**F-1 — the two `reason` enums share a namespace, and that overlap is the only thing making `current` load-bearing.** Found while running down the M2 survivor (below), not by reading the criteria list. `composeBuild` (server.js:111-128) copies `deployState.reason` verbatim on the good path but *overrides* it with its own judgements — `stale-state`, `no-watcher`, `unknown-build`, `no-state`, `unreadable-state` — on the degraded paths. Nothing stops the watcher's file from spelling one of the server's words. I drove `composeBuild` over **6,656 input combinations** (buildId × desiredId × reason × computedAt × deploy-state shape × watcherListening): **119 distinct `(id, desiredId, reason)` triples**, of which **12 map to more than one `current`** — and all 12 are that collision shape. Receipt: `scratchpad/agent-developer-lena/AS-85/m2-probe.mjs`. Two consequences worth Owen's and Ruben's eyes:
- (a) For **every reason the watcher actually writes today** (`current`, `busy`, `stale-build`, `cooldown`, `no-git`, `inputs-dirty`, `no-docker`), `current` is a pure function of `id`, `desiredId` and `reason` — i.e. once B2 puts `reason` in the key, `current` is redundant in production and is load-bearing only on an input the watcher never produces. It stays in the key (removing it is a design change outside this plan, and it is the field the client's tri-state contract is written against), but the plan's framing of criterion 4 as a straightforward property does not hold.
- (b) A client that reads `reason: 'stale-state'` cannot tell whether the *server* judged the file stale or the *watcher* wrote that word. Suggested follow-up, not done here (out of scope): namespace the server's own judgements, or move them to a separate `freshness` field. Happy to file it if the CTO wants it.

**F-2 — plan §3.3 step B3 as written leaves M3 unkillable (erratum).** The table has B3 write `desiredId: 'cccc…', reason: 'stale-build'` and calls it "`desiredId` only" — but B2 has just set `reason` to `'busy'`, so B3 as specified moves two key fields and a `desiredId`-less key still changes. Implemented B3 as `desiredId: 'cccc…', reason: 'busy'` (a real watcher state: master moved again while a rebuild is running). M3 is red at B3 as a result.

**F-3 — plan §3.3 step B4 as written leaves M2 unkillable (erratum; the M2 survivor).** B4 is labelled "`current` only (false→null)", but the stale path returns `{...out, reason: 'stale-state'}`, so `reason` moves with `current` and the first battery's M2 survived with the mutation correctly applied at line 582. Per the survivor rule I re-read the mutated file before concluding anything — the mutant was at the intended and only site — then ran the F-1 probe, which found the one shape that isolates `current`: a file whose `reason` already reads `'stale-state'`, crossed over the 10-minute staleness edge. Added **B5** (fresh, `reason: 'stale-state'` → `current` true) and **B6** (same body 11 minutes old → `current` null, `reason` unchanged because it already matched the override, `id`/`desiredId`/`listening`/`state` all held). M2 is now red at exactly B6. Criterion 4 is met by an observed red, but at a different step than the plan named, and F-1(a) is why.

**F-4 — the fixture writes `deploy-state.json` the way the watcher does (`.tmp` + `renameSync`), deliberately.** `advance-watcher.mjs` writes it atomically; a plain `writeFileSync` read mid-poll parses as garbage, which `composeBuild` reports as `reason: 'unreadable-state'` — a genuine key change and a frame Test A would have blamed on the guard. At ten rewrites against a 25 ms poll that is a live flake, not a theoretical one. Mirroring the producer removes it.

**F-5 — trivia.** The plan's Test A title names `runningId` among the churned fields while §3.2 step 2 held it fixed. I kept the title verbatim and churned `runningId` too (it is inert for `composeBuild`), so the name is true and the churn is strictly wider. Also: the Test B step helper now wraps a missing frame with its own label — the bare `nextFrame` timeout carries only a timer stack, so a future red would not have said *which* field stopped earning a frame.

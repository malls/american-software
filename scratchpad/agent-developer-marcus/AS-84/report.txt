== FINDINGS (7; 1 is a correctness deviation from the plan, 3 are red-set corrections to the plan's predictions, 3 are implementation notes a reviewer should know before reading the diff) ==

F-1 (deviation from plan §2.1, and the plan is internally inconsistent here). The plan says performDeploy "sees signal !== null in the result and records outcome 'aborted'". I did NOT implement that test. A child that traps SIGTERM and exits with a code reports signal null and a code — and that is exactly what the plan's own AC-14 fake docker does (trap 'exit 143' TERM), and what a real `docker compose` child does when it handles the signal. Under the plan's literal rule the AS-84 process test would have recorded the interruption as outcome 'fail' and put the merged build in a 30-minute cooldown, which is the precise harm §2.1 exists to prevent. Implemented instead: `if (abortSignal !== null && !result.timedOut)` — "did WE ask for this", not "how did it die". A timeout stays a failure (nobody asked for that one). Covered twice: the AC-6 unit test gained an assertion for the trap shape (code 143 / signal null -> 'aborted'), and AC-14 exercises it in a real process. M6b is the falsifier for the outcome value.

F-2 (red-set correction, AC-9's falsifier M9). Plan predicts red {AC-9, AC-10, AC-11}. Observed red {AC-9, AC-10, AC-12, AC-14}. AC-11 CANNOT participate in this mutant: it has no child and no deploy in flight, so shutdown takes the synchronous fast path both before and after the mutation — the prediction was wrong, the guard is not weak. AC-11's own falsifier is M1, and it is red there (observed, below). The two additions are honest kills: AC-12 asserts the async contract (assert.rejects on a shutdown that the mutant makes throw synchronously) and AC-14 loses the deploy wait.

F-3 (red-set correction, AC-6's two falsifiers M6a/M6b). Plan predicts {AC-6} for each. Observed {AC-6, AC-14} for both — AC-14 asserts the orphan's absence AND lastAttempt.outcome === 'aborted', so it catches the un-signalled child and the mis-recorded outcome alike. Wider than predicted, in the good direction.

F-4 (how M12's kill presents). AC-12's falsifier kills by TIMEOUT, which node:test reports as `cancelled 1`, not `fail 1`: the summary reads tests 511 / pass 510 / fail 0 / cancelled 1. A reviewer grepping only for "fail" would read that mutant as a survivor. It is not — the failing-tests block names AC-12 explicitly and the test output carries 'test timed out after 5000ms'.

F-5 (implementation note, not in the plan). performDeploy takes a second parameter, `stateFields`, and the pre-build persist() repeats the fields evaluate() just wrote. A bare persist() writes persist's own defaults for everything it is not given, which would reset `reason` to 'no-git' and drop `runningId` for the whole duration of every build — the sidebar's build line would go wrong every time the watcher deployed. AC-5 asserts the record, not the surrounding fields, so this would not have been caught by the criteria list.

F-6 (implementation note). main()'s two signal handlers are now `() => void watcher.shutdown(...)`; plan §2.1 said "main ignores it", and this is that, made explicit. Semantics unchanged.

F-7 (test-harness changes a reviewer will see in the diff). (a) watcherHarness's teardown now calls shutdown, then emits 'exit' on a still-live fake child, then awaits — without it every test that leaves a child in flight would pay the full 10 s grace at teardown, and the injected exit()'s ExitSignal now arrives as a rejection rather than a throw on the async path. (b) deployHarness gained a `preState` option: ctor hydration can only be tested by a state file that exists BEFORE makeDeployOps runs. (c) h.stop() returns shutdown()'s promise.

Seam (plan §6): nothing hard-codes the image-input count — AC-14 builds its fixture by iterating the exported IMAGE_INPUTS, and the new deploy-ops tests are appended at the TAIL of the deploy-ops block, away from the AS-75 parseLsTree test AS-86 is editing. The only shared file regions with AS-86 are makeDeployOps' parameter list (I added `readState`) and the deployHarness signature.

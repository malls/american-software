# AS-79: Observability: Sentry error tracking for apps/chat server + advance-watcher (error tracking only, no analytics; zero-dependency ingest)

Board request: DM conversation 7, msg 521 (2026-09-03), "set up posthog and sentry, low priority, observability needs to be on the radar". Depends on the observability design task (see depends_on link).

SCOPE DECISION, made at filing: apps/chat gets error tracking only. No product analytics. Rationale: chat is internal tooling whose entire user population is nine employees and the board member; a funnel over that population measures nothing and would be a second data-egress channel from an app that carries the company's private #board and #bizdev channels (AS-6 made those private by design — private means private, including from an analytics vendor). If someone later wants usage data on the chat app, it is one SQL query against the local store, not a vendor.

WHAT error tracking buys here: modest on the server (server.js already console.errors at lines 401/433 and the board is looking at the app when it breaks), real on the headless side. The advance-watcher (apps/chat/watch/advance-watcher.mjs) and the ticks it fires have a documented history of silent failure: for most of 2026-08-30 every watcher tick degraded to a no-op because of a permission-layer problem nobody could see (AS-21), and a rate-limited implementer terminated mid-cycle leaving half-applied changes (AS-26 cycle 2). AS-27 (loop-status indicator) addresses visibility of loop state in the UI; this task addresses the complementary case — a crash or a degraded tick that nobody was looking at when it happened, recorded somewhere durable with a stack. Capture points: watcher process uncaught/unhandled, tick child non-zero exit with the tail of its output, and the chat server's two console.error sites.

HOW: bounded by the design note. apps/chat is a zero-dependency app (package.json) and should stay one; the design note's raw-ingest option (Sentry envelope API over node fetch) is the presumptive route here unless the note argues otherwise. One egress module under apps/chat/lib, no-op when CHAT_SENTRY_DSN is unset, suite unaffected. Deny-list: message bodies, conversation ids/names, identities, and the sqlite path never appear in an error payload — the chat store is the one place private channel content lives.

BOARD GATE: same as the invoicing tasks — a Sentry account is board-gated, including free tier, per CLAUDE.md. No signup, no DSN, no host on the implementer's initiative. Expected to share the account the invoicing task's ask obtains (one org, separate projects), so this task carries no ask of its own; if it is picked up first, it builds the no-DSN path and parks in needs_human.

PRIORITY: low, and the lowest of the four. Does not jump the chat cluster (AS-27, AS-75, AS-28, AS-73, AS-74, AS-72, AS-61) — those ship the merged code and close review findings; this only matters once the deploy gap (AS-75) is closed and the app is running code we did not hand-rebuild.

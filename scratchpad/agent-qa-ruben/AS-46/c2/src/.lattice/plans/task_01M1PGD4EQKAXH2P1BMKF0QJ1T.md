# AS-83: Chat: mode.test.js AS-24 case is flaky under concurrent docker build

Planner: agent:cto-owen (tech lead), 2026-09-11, against master e5de119 (board-only commit on top of 5c98662; `apps/chat` code identical). Complexity: medium — the diff is small; the reproduction is the work.
Source: four independent observations across three tasks (task description + comments; Priya ×2, Lena, Marcus; Ruben saw the same shape 5/14 on AS-93 and declined to file solo). All in `apps/chat`. Planning stage ran no docker (a concurrent build is this task's own flake condition and Ruben's AS-73 counted run was in flight); every load claim below is therefore a *prediction* the implementer must observe before fixing.

## 1. What is known (evidence, not conclusions)

- The failing assertion is `assert.equal(dm.status, 0, dm.stderr)` at `test/mode.test.js:93` — the **first** spawned CLI child of the case, exit status non-zero. Passing duration ≈ 3000 ms for four sequential spawns (≈ 750 ms each on emulated linux/amd64); failing at ≈ 1350 ms ≈ `bootServer` + one child that lived ≈ 1200 ms and exited. The child exits early; it does not hang.
- The child's only wall-clock-bounded step is the probe: `lib/client.js:48` `fetch(base + '/api/identities', { signal: AbortSignal.timeout(PROBE_TIMEOUT_MS) })` with `PROBE_TIMEOUT_MS = 500` (`client.js:21`). Every later call in `createApiBackend.call` (`client.js:95–111`) has no signal and cannot time out. A `TimeoutError` has no `.code` in `DOWN_CODES`, so `isConnDown` is false and `probe` returns `'ambiguous'` (`client.js:49–50`); under rule 3 (`CHAT_API` set, `bin/chat.js:133–138`) ambiguity is `fail(REFUSAL(api))` — stderr "something is listening … but the probe failed; refusing to touch the shared DB", exit 1, zero side effects. Predicted child timeline under a 500 ms timeout: ≈ 650–750 ms node start-up (emulated) + 500 ms budget + exit ≈ 1150–1300 ms. That is the observed number.
- The server is provably listening before the child is spawned (`bootServer` awaits `listen`, `mode.test.js:49`), so ECONNREFUSED (→ `'down'` → direct mode → **exit 0**) cannot produce a non-zero status. Ruled out.
- A lazy first-request cost is ruled out: `ingestNewEvents` runs synchronously before `listen` and stamps `lastIngest` at boot (`server.js:263–276`), so no request within 10 s of boot pays an ingest. `/api/identities` is one `store.listIdentities()` (`server.js:726–727`).
- Load model: the compose `test` service (`compose.yaml:84–89`) runs `node --test` under `platform: linux/amd64`, emulated on Apple Silicon; Node's runner puts each of the 31 test files in its own process (default concurrency `availableParallelism() − 1`), so the container is already CPU-saturated on its own, and a concurrent `docker compose build` adds BuildKit's work on the same VM. The parent process hosting the in-process server is one of those 31 and competes for the same emulated cores; its event loop has to accept, route and answer inside the child's 500 ms.
- **Legibility**: the assertion *does* already pass `dm.stderr` as the message — yet none of the four sightings quoted it. If the child had died by signal, `status` is `null` and stderr may be empty, leaving the default `1 !== 0` text. Whatever the mechanism, the current message loses elapsed time, signal, and stdout, and the refusal text itself does not say *why* the probe failed (timeout vs 5xx vs wrong shape). The next sighting must name the exit path without a re-run.

## 2. Hypotheses, ranked

- **H1 (primary): probe budget exceeded under CPU contention → `'ambiguous'` → rule-3 refusal, exit 1.** Evidence: the timing arithmetic above lands on the observed 1350 ms; the only timeout in the child is the probe; the refusal path is the only exit-1 path that leaves stdout empty and touches no DB (consistent with no observer reporting a stray DB or a JSON parse error at line 94); reproduces only where CPU is emulated *and* contended. Priya's third-observation framing is the same hypothesis.
- **H2: parent event-loop stall in the test process itself** (the server's loop blocked by something in the same process — a synchronous store call, GC under memory pressure) long enough to blow the same 500 ms. Same symptom and same fix as H1; distinguished only by *where* the latency is, and the reproduction below measures the probe latency directly so the two are told apart by the number, not by argument.
- **H3: the child killed or failed to start under memory pressure** (`status === null` + signal, or an early node crash). Weak: nothing in four sightings mentions `null`, and a signal kill has no reason to land at 1350 ms. The legibility change (§3 step 1) makes this either visible or dead at the next sighting.
- **Ruled out**: ECONNREFUSED (server is listening before spawn); a lazy first-request ingest (`server.js:265`); DNS (loopback literal); any timeout in the command calls after the probe (none exist).

## 3. Approach

The fix has to satisfy two things at once: production stops refusing a *slow* server as if it were *ambiguous* (this bites the real host CLI too — a tick's `chat.js` call during a watcher rebuild is exactly a probe racing a loaded docker daemon), and the test stops depending on the wall clock while still going red the instant CLI writes bypass the server. Timeouts can only ever produce *refusals* (exit 1, nothing written) — no probe budget value can turn `'ambiguous'` into `'down'`, because `'down'` requires a positive ECONNREFUSED/ENOTFOUND. That is the reason a wider probe budget cannot mask a mode regression, and §5 AC-7 proves it by mutation rather than by this sentence.

1. **Make the failure legible** (`test/mode.test.js`). `run()` records `startedAt` and returns `elapsedMs` and `signal` alongside `status/stdout/stderr`. Add `describeExit(r, label)` → one string: `${label}: exit ${status} signal ${signal} after ${elapsedMs} ms\n--- stderr ---\n…\n--- stdout ---\n…`. Every `assert.equal(x.status, 0, x.stderr)` in the file (lines 93, 111, 118, 194, 227, 270, 282, 296, 334, 354, 364, 368, 380, 388, 410 — verify the list with `grep -n "status, 0, " test/mode.test.js`) becomes `assert.equal(x.status, 0, describeExit(x, '<cmd>'))`.
2. **Make the refusal say why** (`lib/client.js`, `bin/chat.js`). `probe(base, { timeoutMs = DEFAULT_PROBE_TIMEOUT_MS } = {})` returns `{ state, reason }` where `state ∈ {'up','down','ambiguous'}` and `reason` is `null` for `'up'`, else a short string: `timed out after ${timeoutMs} ms` (when `e.name === 'TimeoutError'`), `HTTP ${res.status}`, `wrong shape`, `unparseable body`, or `${code ?? e.message}`. Update the three call sites in `resolveBackend` (`chat.js:125, 134, 140`) to read `.state`; `REFUSAL(base, reason)` and the `CHAT_MODE=api` message append ` (${reason})`. The four existing refusal assertions (`/AS-24/`, `/refusing to touch the shared DB/`, `/CHAT_MODE=direct/`, `/CHAT_MODE=api/`) keep matching — the reason is appended, not substituted.
3. **Raise the production budget and expose it as a knob.** `export const DEFAULT_PROBE_TIMEOUT_MS = 3000` in `client.js` (replaces the private `PROBE_TIMEOUT_MS = 500`). `resolveBackend` reads `CHAT_PROBE_TIMEOUT_MS`: unset/empty → default; a positive integer string → that many ms; anything else → `fail(\`chat: invalid CHAT_PROBE_TIMEOUT_MS '${v}' — a positive integer of milliseconds (AS-83).\`)`, validated up front next to the `CHAT_MODE` check (`chat.js:120–122`) so it is a usage error on every path, including `CHAT_MODE=direct` where it is never used. Document the knob in the usage text (`chat.js:56–60`) and in the mode-rule header comment (`chat.js:14–22`). **The default is a decision with a time-box:** 3000 ms stands unless the §6 R0 measurement shows a p99 probe latency under induced load above 1000 ms, in which case the implementer sets `ceil(3 × p99 / 500) × 500` and records the numbers in the implementation comment. Cost of the raise: a listener that accepts and never answers (the trap case) now costs the CLI up to 3 s instead of 0.5 s before it refuses. Accepted — that case is pathological, and the refusal semantics are unchanged.
4. **Decouple the up-path tests from the wall clock.** In `mode.test.js`, the two cases that need the in-process server to be *up* (the AS-24 case at line 86 and the full command sweep at line 256) pass `CHAT_PROBE_TIMEOUT_MS: '20000'` through one shared `apiEnv(base, phantom)` helper (single occurrence — it is also the M4 mutation anchor, §6). A live in-process server that takes > 20 s to answer one GET is not load, it is a hang, and it still ends as a legible exit 1 naming the budget rather than a runner wedge. The trap case (line 134) sets **no** knob so it proves the default applies when unset — it now costs ≈ 3 s on the host and asserts `timed out after ${DEFAULT_PROBE_TIMEOUT_MS} ms` via the imported constant, so the number is pinned by one source.
5. **Pin the flake signature as a permanent, deterministic test** — a slow-but-live server, not a tiny budget racing a fast loopback (a 1 ms budget against a local server is itself a race in the other direction). A `slowProxy(t, targetPort, delayMs)` helper: raw TCP server that on `connection` waits `delayMs` then connects to the real server and pipes both ways; tracks sockets and destroys them on teardown (the trap-case pattern, lines 138–144). Delay 150 ms. Two cases (§4 T1/T2): budget 50 ms → the exact observed signature; budget 20 000 ms → up, write lands in the server view. Same server, same proxy, only the budget differs — that *is* the flake, written down.

**Which timeouts may move, and which must not.** May move: `DEFAULT_PROBE_TIMEOUT_MS` (production default), `CHAT_PROBE_TIMEOUT_MS` (per-invocation override), and the values the tests pass. Must not move, in code or in meaning: a probe timeout is `'ambiguous'`, never `'down'`; `'ambiguous'` is `fail()` with exit 1, empty stdout, and no store opened, on every rule (`chat.js:125–129, 137, 143`); `'down'` requires a positive `ECONNREFUSED`/`ENOTFOUND` (`client.js:23, 28–34`); `'up'` requires 2xx **and** the `{identities: […]}` shape (`client.js:52–59`); one mode decision per invocation and no mid-command fallback (`client.js:103–111` gains no timeout and no retry); `CHAT_MODE=direct` skips the probe entirely; rule 4 (`CHAT_DB` alone) stays probe-free. No retry loop is added to the probe (§9).

## 11. Decisions and deliberate omissions

- **No retry loop in the probe.** A retry multiplies the trap cost and adds nothing a larger budget does not; a slow-but-live server is answered by a budget, and a never-answering one is refused either way.
- **No timeout on `createApiBackend.call`.** Mid-command server loss is already a `StoreError` with the AS-24 wording; adding a per-call timeout is a different property with its own falsifiers, and nothing observed points at it.
- **`node --test` concurrency in the image is unchanged.** `--test-concurrency=1` would lower the load and probably hide the flake — that is masking, not fixing — and it would slow every counted run.
- **The production analog is observed in the field, not in the suite.** A host `chat.js` call during a watcher rebuild is the same race; after this change a refusal in a tick log names `timed out after N ms`, which is the evidence that would reopen the default. Open question, time-boxed: is 3000 ms right for the host CLI? Default answer: yes; revisit only on a field refusal naming the timeout.
- **A tiny-budget race was rejected as the signature test** (T1 uses a delaying proxy instead): `CHAT_PROBE_TIMEOUT_MS=1` against a fast loopback server can win, which would make the flake test itself flaky.
- **Compose healthcheck untouched** — it has its own 5 s timeout and is not on this path.
- **The AS-73 roster-parity case** (`CHAT_API` without `CHAT_DB`) is out of scope, but the M1 note in AC-12 exists because of it: mutation runs are confined to `mode.test.js`, and the worktree's `data/` is checked clean afterwards.

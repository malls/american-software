THE PROBLEM, STATED CORRECTLY. The dashboard port is not one value in one place. It is a three-legged coupling and no leg alone is authoritative:
  L1  the port `lattice dashboard` binds. CLI flag `--port`, default 8799 (verified: lattice/cli/dashboard_cmd.py:49; `lattice restart` defaults to the same at :143). Today supplied by hand in a live session; after AS-94 it is declared by the launchd plist.
  L2  the Tailscale serve mapping that publishes it on the tailnet. Verified live: `https://forrests-newer-macbook.tail3f3c29.ts.net:8443 -> http://127.0.0.1:8799`. This state lives in tailscaled, NOT in this repo, and chat cannot read it.
  L3  the two constants in apps/chat/public/dashboard-link.js: LOOPBACK_PORT=8799, REMOTE_PORT=8443.
Move L1 without L2 and the phone breaks. Move L1 and L2 without L3 and both break. LATTICE_DASHBOARD_URL does not solve it: it is a single verbatim base, so it can express "this one URL everywhere" but never "port X on loopback, port Y over the tailnet" — setting it to a loopback URL with a new port fixes the Mac and re-breaks the phone.

WHY THIS IS NOT JUST "ADD A CONFIG KEY". The obvious move — have the server publish `latticeDashboardPort` over the /api/config channel AS-93 already builds, and let the client compose `:port` locally — removes the hard-coding in L3 only. The tailnet link stays correct only if L2 moved too, and nothing in the repo can observe L2. That is a knob that reads as a fix and is not one. So the scope here is the coupling, not the constant:
  - ONE declared value that L1 and L3 both read (candidate: an env value consumed by the launchd plist render and published to the browser via /api/config, with the client deriving `:port` for a loopback page and keeping the tailnet port from the same declaration).
  - L2 handled honestly: either it becomes a repo artifact with a render/verify recipe (AS-94 currently lists that as OUT of scope — revisit here, do not silently import it), or it stays host state and the docs name it as the one leg that must be moved by hand, in the same procedure, with the check that proves it moved.
  - Precedence with LATTICE_DASHBOARD_URL settled in writing BEFORE any code: a verbatim base override and a port declaration can contradict each other, and AS-93's rule 1 (override wins verbatim) must either survive or be deliberately replaced. An unstated precedence rule is how this comes back a third time.

WHAT ALREADY EXISTS AND MUST BE REUSED, NOT REBUILT (this is why merging AS-93 first costs nothing):
  - apps/chat/public/dashboard-link.js is a pure module and the SINGLE point of change — the two ports are exported constants and AS-93's AC-9 bans 8799/8443/127.0.0.1 literals anywhere else in public/, enforced by a test that enumerates the directory. There is no second place to fix.
  - GET /api/config exists, with an explicit allowlist and an exact-key-set assertion in test/api.test.js standing guard over it. A new key is an additive change to a guarded channel.
  - AS-94's plist template is where L1 gets declared, and its AC-2 already asserts the rendered ProgramArguments.

The planner writes them, and per M4 each stated property names its own falsifier — including at least one that observes a link go WRONG when one of the three legs is moved alone, since "the legs are coupled" is the entire claim this task makes.

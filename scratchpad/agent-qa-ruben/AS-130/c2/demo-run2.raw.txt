D1 core-loop walkthrough (AS-90)
================================

WHAT THIS DEMO CAN SHOW
- The whole server-side core loop working end to end on this codebase: sign up, session,
  Connect onboarding start, readiness, client, contract, invoice draft -> finalize -> send -> paid.
- All seven screens in a real browser, in the states this same walk reaches, at phone and desktop
  widths: sign in / sign up, Connect Stripe, dashboard, invoice form, invoice detail, contract form,
  contract detail (with its print view).
- The contract document the app generates.
- The custody guard: the platform key never charges anyone. Every Stripe request the app made
  is listed at the end, and none of them moves money.
WHAT THIS DEMO CANNOT SHOW
- A real Stripe onboarding round trip, a real hosted invoice page, a real payment, or a real
  webhook delivery. There is no Stripe account in this run, by design; a run against a Stripe
  test-mode account is a separate, later step; every Stripe call here goes to Stripe's own
  request validator (stripe-mock), which checks shapes and answers with fixtures.
- Email of any kind. There is no email provider, by design.
- The "connected" and "paid" states are produced by events WE signed. They prove our receiver and our
  state machine, not Stripe's delivery.

This walkthrough boots the same application code, from the same shipped image, inside a container that sits next to a Stripe request validator and has no route to the internet. Every request below is a real HTTP request to the real routes; the database is a fresh file created for this run.

Every step carries one of three labels:
  REAL APP BEHAVIOUR — the app's own code did this; it would do the same against real Stripe.
  STRIPE-MOCK STAND-IN — Stripe's request validator answered with a fixture; real Stripe would answer with real data, and the step says what would differ.
  SYNTHESIZED EVENT — we built and signed this event ourselves; it proves our receiver and state machine, not Stripe's delivery.

App: http://127.0.0.1:45517 (loopback, inside the container). Stripe host: http://stripe-mock:12111 (stripe-mock).
Freelancer: Dana Reyes <dana@demo.example>. Client: Northwind Studio <billing@northwind.example>.

[1/12] Sign up
REAL APP BEHAVIOUR
  A freelancer creates an account with a display name, an email address and a password. The password is hashed with scrypt before it is stored; the response sets an HttpOnly session cookie and sends the browser to the landing page.
  > POST /signup  displayName=Dana Reyes  email=dana@demo.example  password=••••••••
  < 303  Location: /  Set-Cookie: invoicing_session=… (Path=/; HttpOnly; SameSite=Lax)

[2/12] Session
REAL APP BEHAVIOUR
  The same browser asks for the landing page. With the cookie it is let in; without it, the auth boundary sends it to sign in. (The landing page is the dashboard, screen 3; with nothing created yet it renders its first-run empty state.)
  > GET /  (with the session cookie)
  < 200  body: text/html, 1649 bytes, page state S3-EMPTY-FIRSTRUN
  > GET /  (without a cookie)
  < 303  Location: /signin?next=%2F

[3/12] Connect onboarding start
STRIPE-MOCK STAND-IN
  The freelancer clicks "Connect Stripe". The app creates a connected account on the platform and asks Stripe for a one-time hosted-onboarding link, then redirects the browser to it. Here Stripe's request validator checked both request shapes and answered with fixtures: the Location below is a fixture URL, not a page anyone can open, and no hosted onboarding happens.
  > POST /connect-stripe/start
  < 303  Location: https://sangeekp-15t6ai--manage-mydev.dev.stripe.me/setup/s/acct_1PgafTB7WZ01zgkW/MerI6itPZo2K

    POST /v1/accounts
    POST /v1/account_links
  connected account recorded: acct_RM7nW6EeWRon49w (read from the app's database)

[4/12] Connect onboarding return
STRIPE-MOCK STAND-IN
  Stripe sends the freelancer back after hosted onboarding. The app never trusts the return itself: it re-reads the account from Stripe and stores what it finds. The validator's account fixture is NOT ready — requirements still due, charges disabled — which is exactly how a freelancer who has not finished Stripe's identity checks looks. Real Stripe would answer with the real account state. The Location header is the contract; in a browser it lands on screen 2 (Connect Stripe), shown in the screenshots.
  > GET /connect-stripe/return
  < 303  Location: /connect-stripe
  Stripe requests the app made:
    GET /v1/accounts/acct_RM7nW6EeWRon49w
  readiness recorded (read from the app's database): ready=false, charges_enabled=false, requirements currently due: 6

[5/12] Readiness
SYNTHESIZED EVENT
  When a freelancer finishes onboarding, Stripe delivers an account.updated webhook. We built and signed that event ourselves — with the same signing scheme Stripe uses — describing the account as ready, and posted it to the app's receiver. The receiver verified the signature, recorded the event id so a redelivery cannot apply twice, and updated readiness. This proves our receiver and our state machine, not Stripe's delivery.
  event evt_demo_account_ready type account.updated for acct_RM7nW6EeWRon49w: charges_enabled true, details_submitted true, payouts_enabled true, requirements currently due: none
  Stripe-Signature: t=1789254335,v1=4124e440dc2cb4c482e5f6072f221a633789688e7f3ad291cfca83e9cade0f82
  > POST /webhooks/stripe  (body: the signed event JSON)
  < 200  body: "ok: readiness"
  readiness recorded (read from the app's database): ready=true

[8/12] Invoice draft
REAL APP BEHAVIOUR
  The freelancer drafts an invoice: one line item, priced in integer minor units (cents), due in 30 days. A draft is local — the app makes no Stripe request until the freelancer issues it. The amount is $10.00 because stripe-mock's invoice fixture always reports amount_due 1000 and the app refuses to finalize an invoice whose total disagrees with Stripe. The Location header is the contract; in a browser it lands on screen 4 (invoice form), shown in the screenshots.
  > POST /invoices  clientId=a8281b24-cb56-400d-86b5-c2efb6953bf2  daysUntilDue=30  currency=usd  lineItems[0][description]=Website redesign — milestone 1  lineItems[0][quantity]=1  lineItems[0][unitAmountMinor]=1000
  < 303  Location: /invoices/de3155ab-ad0a-40de-a7ae-9d6fe269df4d/edit
  Stripe requests the app made: none

[10/12] Send
STRIPE-MOCK STAND-IN
  The freelancer sends the invoice. Real Stripe would email the client a hosted payment page; the validator only checked the request shape. The app records when it asked, from its own clock. No email of any kind is sent by this app, by design. Three requests appear below instead of one, and that is a mock artifact: the app's pipeline is resumable and re-runs "add line item" and "finalize" whenever the mirror still says "draft" — which it does here only because the validator's fixture never advances to "open". Against real Stripe this step makes exactly one request.

### 3. Issues

**[minor] apps/chat/public/lanes.js:96–110 and apps/chat/public/app.js:1019 — `git-error` renders as `Lanes · 0` / "No lanes in flight."**
`composeLanes` follows plan T4/AC-11 and returns `lanes: [], count: 0` when the snapshot carries `error`. `describeLanes` then takes the `lanes !== null` path and emits badge `Lanes · 0` (verified: `git-error badge: Lanes · 0`), and `renderLanes` keys its empty text on the badge string, so the pane prints "No lanes in flight." under a caption that says git refused. That is exactly the "0 is a measurement" confusion the module's own header and AC-14 forbid; the task-only lanes are also dropped in this state, so the count is not even the Lattice half. The caption is correct and stale-styled, so the board is not misled if they read the second line — but the badge is the ambient glance.
**Fix:** in `describeLanes`, treat `reason === 'git-error'` like the `lanes === null` branch for the badge (`Lanes · –`, title = the git-error sentence) while still returning `lanes: []`; in `renderLanes`, choose the empty text from `view.stale`/reason (`'No lane data to show.'` when the reason is not `ok`), not from the badge string. Add a `lanes-label-git-error-is-dash` case beside `lanes-label-null-is-dash`.

**[minor] apps/chat/public/lanes.js:171–175 — a merged lane's last-commit field reads "no commits on branch yet"**
`ahead === 0` is used as the proxy for "nothing committed on this branch", but a `--no-ff`-merged branch also has `ahead 0` (its commits are all on master now). For the STALE/merged case the card shows `STALE — its branch is already merged into master` and, two rows down, `no commits on branch yet (tip by developer-lena, 1 h ago)` (verified by probe). The two statements contradict each other on the same card.
**Fix:** branch on `wt.merged === true` first (e.g. `merged — tip by ${who}, ${when} ago — ${subject}`), and only fall to "no commits on branch yet" when `ahead === 0 && merged !== true`. One assertion in `lanes-label-stale-badge-says-why` covers it.

**[minor] apps/chat/lib/lanes.js:80–84 — `lastCommit` is copied through un-whitelisted**
`worktreeView` whitelists the eleven top-level keys (AC-13, asserted), but `lastCommit` is the snapshot's object verbatim. A field the watcher grows inside `lastCommit` tomorrow (the plan's own example of what the whitelist exists to stop) reaches the browser; `api-lanes-key-whitelist` only asserts top-level keys, so it would not go red.
**Fix:** project `lastCommit` through an explicit `{sha, authorName, authorEmail, committedAt, subject}` pick and extend the whitelist test to `Object.keys(lane.worktree.lastCommit)`.

**[minor] apps/chat/watch/advance-watcher.mjs:1525–1531 — `relPathOf` compares raw strings, so a symlinked or differently-spelled `repoRoot` leaks the absolute host path**
`git worktree list` prints the path as git recorded it; `config.repoRoot` comes from `import.meta.url` or `ADVANCE_REPO_ROOT`. If the two differ (`/var` vs `/private/var`, an env override with a symlink, a different case on APFS), the `startsWith` fails and `relPath` becomes the absolute host path — the one thing T4 says stays out of the snapshot. Today on this host they match (probe showed `.worktrees/AS-28`), so this is latent.
**Fix:** `realpathSync` both sides once in `makeLanesOps` (guarded, falling back to the raw string), or assert in `evaluate` that a non-relative `relPath` is replaced by `basename` plus an `errors[]` entry.

SOURCE: board DM msg 793 (human:forrest, 2026-09-11T18:15Z), verbatim: "I think we need to make commit hashes/branch names in chat messages clickable to copy. make an issue for this". Filed by cto-owen on the board's behalf (acked in msg 810).

WHAT "CLICKABLE TO COPY" MEANS, concretely:
  - A recognised commit hash (a bare 7-40 character lowercase hex run, word-bounded) or a branch name of the company's shape (feat/AS-<n>-<slug>; the planner decides whether to also admit other prefixes seen in history, e.g. records/ or fix/, and should grep the chat export to find out what shapes actually occur) inside a message body renders as an inline element that, on plain click, writes the LITERAL matched text to the clipboard and shows a brief visual confirmation (e.g. a short-lived "copied" state on the element). No navigation, no href, no new tab. Modified clicks and text selection keep working as today.
  - Copy uses navigator.clipboard.writeText where available; the planner decides the fallback (execCommand('copy') on a selection, or simply no affordance) for insecure contexts -- the tailnet page is https and the loopback page is http://127.0.0.1, which browsers treat as a secure context, so both real deployments should have the async clipboard API.

WHY: the board reads commit hashes and branch names in tick reports, review comments echoed into #engineering, and the lattice-events channel, and wants to paste them into a terminal without drag-selecting a 7-character token on a phone or a laptop. Selection of short hex runs is fiddly on touch; a one-tap copy removes it.

TENSION WITH THE SAME-DAY "WRITING TO THE BOARD" RULE (#board msg 794, CLAUDE.md § Writing to the board): board-facing messages (DMs to human:forrest, #board, #bizdev) should no longer carry commit hashes or branch names at all -- the evidence moves to the Lattice task. That does NOT make this affordance moot: #engineering, employee-to-employee DMs, and the lattice-events channel (which mirrors board commits verbatim, e.g. "merged 74cb6f9") still carry hashes and branch names by design, and the board reads those channels too. The affordance is worth having; the planner should not re-derive this.

WHERE RENDERING HAPPENS (the seam the planner starts from):
  - apps/chat/public/app.js bodyNode(message) is the single body renderer. It runs tokenizeInline (public/markdown.js: code / strong / em / link, code first, single level) over the whole body, then appendRefLeaf(parent, text, refs, {autolink}) over every plain-text leaf INCLUDING the inner of code/strong/em/link spans. appendRefLeaf is a fixed chain of pure tokenizers, in a recorded order: tokenizeUrls (AS-54, terminal -- URL text is never fed further) -> tokenizeAsRefs (AS-10, matches only refs the server resolved) -> tokenizeMsgRefs (AS-26, "msg 156") -> tokenizeFileRefs (AS-26 §5, public/msg-refs.js FILE_RE, .md paths only) -> createTextNode. A hash/branch pass would be one more link in this chain, and its position matters: it must run after the URL pass (a hex run inside a GitHub commit URL must stay part of the URL) and must not steal "AS-87" out of "feat/AS-87-deploy-heartbeat-and-log" -- i.e. the branch tokenizer probably belongs BEFORE tokenizeAsRefs, and the hash tokenizer after msg-refs so "msg 810" digits are never read as hex. Order is an acceptance-criterion-grade decision, with named falsifiers per M4.
  - Invariants to preserve: tokenizers emit text and structure, never markup (zero innerHTML anywhere -- every node via el()/textContent/createTextNode); every token's text is the exact source slice so concatenation round-trips the input; tokenizers are pure modules importable from node:test (existing tests: test/markdown.test.js, test/msg-refs.test.js). Put the new tokenizer(s) in msg-refs.js or a sibling pure module with the same contract so they are unit-testable without a DOM.
  - Hash false positives are the real design question: seven-letter English words made only of a-f (e.g. "decade", "facade", "deface" -- 6 letters; the 7+ cases are rarer but exist, and any all-digit run of 7+ like a pid 2147483648 or a timestamp matches a pure-hex regex). The planner should decide the rule (require at least one digit AND one a-f letter? minimum length 7? word-boundary and not preceded by '#'/'msg'?) and, per M4, name the concrete inputs that must NOT tokenize as a numbered criterion. Grep apps/chat/data/export/ for real bodies to calibrate.

STYLING: BRANDING.md governs the affordance -- inline code today uses `.body code` (style.css ~L176); a copyable token wants a cursor/hover/"copied" state built from existing semantic tokens (--color-accent-bg-subtle, --color-border-interactive, --color-focus-ring, etc.), no raw hex, no new colors. Keyboard: the element should be focusable and copy on Enter/Space, or the plan says why not.

TESTS: the tokenizers get node:test coverage in the existing style (exact token slices, round-trip, named negative inputs). Clipboard behaviour has no test harness in this suite (no DOM); the plan says what is guarded by tests and what is verified by a recorded manual check, and counts them separately. Every counted suite run carries --build (CLAUDE.md corollary).

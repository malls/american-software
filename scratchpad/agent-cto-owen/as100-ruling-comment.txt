BOARD RULING (DM msg 668, human:forrest, 2026-09-11T01:56Z), answering the time-boxed question at the end of DM msg 663: "I think we'd want both. tool level activity can just be live as it happens, it does not need persistence"

WHAT THIS CHANGES FOR AS-100: nothing in scope. This task remains the PERSISTED stream exactly as filed -- stage-level tick / stage / sub-agent lifecycle events, append-only JSONL, Lattice envelope. The 'EXPLICITLY NOT IN v1' line on tool-level activity still holds for THIS task; tool-level activity is now its own Chat-set task, AS-103, with a different storage rule.

THE TWO-SIGNAL RULE (binding on the AS-99, AS-100 and AS-103 planners):
1. STAGE-LEVEL STATE -- which employee is on which task at which stage in which worktree, since when; tick and sub-agent lifecycle -- is PERSISTED: written to the AS-100 JSONL stream on the host, readable after the fact, projected by the chat server. It is the sole source of truth for the foreman view's employee state machine (idle / planning / building / reviewing / waiting-on-board / blocked) and for stage timers.
2. TOOL-LEVEL ACTIVITY -- an employee reading a file, editing, running tests, waiting on docker -- is LIVE AND EPHEMERAL: it flows through a transient, in-memory channel only -- the chat server's existing SSE fan-out at /api/stream (server.js, the AS-25 `streams` Set), as a distinct event name (proposed `event: activity`), delivered to the connections open at that moment -- and is deliberately NOT written to the JSONL event stream, NOT written to the chat sqlite store, NOT written to any file under apps/chat/data/, .lattice/ or logs/, and NOT replayed to a client that connects later. A client that connects after a tool call learns nothing about it. The board's words are "does not need persistence"; I am tightening that to "must not be persisted" so a planner cannot read it as optional. Reason: a persisted tool-activity log would be a second event stream competing with this one under the 'one stream, many projections' doctrine, at roughly 100x the volume, carrying payloads (commands, paths, contents) nobody decided to make a record.
3. THE FOREMAN VIEW COMPOSES THE TWO: the persisted signal decides which figure stands at which station in which state; the ephemeral signal animates the figure while frames arrive and decays back to the stage-level state after N seconds of silence. A page reload is truthful from signal 1 alone, and shows no history of signal 2.

CONSEQUENCE FOR THIS PLAN: the AS-100 plan names the /api/stream event names for BOTH signals (e.g. `event: company` for persisted AS-100 events, `event: activity` for AS-103's ephemeral frames) so a consumer subscribes to either without guessing, and states that only the former has an HTTP read-back endpoint. The persistence-boundary falsifier (M4) is AS-103's acceptance criterion, not this task's. Nothing else moves; ordering unchanged (fourth, behind AS-99, not before AS-95 lands).

### 3. Issues

**[minor] apps/chat/watch/advance-watcher.mjs:1890 (pendingDeploy) and :1113 (nextPollAction) — a foreign lock is reported as "deploy pending" and bypasses the F1 lock-wait bound**
`makeDeployOps.evaluate()` passes `busy: busy || lockIsBusy(nowMs)` to `decideDeploy`, so `lastDecision.reason === 'busy'` is set both by our own child *and* by any fresh foreign lock (a live `/loop /advance` session, a manual tick). `pendingDeploy()` treats both as "a rebuild is owed", and `nextPollAction` checks `deployPending` *before* the loop ever reaches `fire()`. Consequences while a foreign live-pid lock is held and docker is resolvable: (1) the loop logs `LOOP-WAIT deploy pending` when nothing is owed — the wrong reason for the board to read; (2) `fire()` is never called, so `aborted()` never runs and the 1-hour `maxLockWaitMs` → `lock-unavailable` stop added for F1 never engages. The wait is not a hang — it ends within one deploy-poll interval (60 s) of the foreign lock clearing — but the "bounded, readable wait" property the F1 fix establishes is only true when docker is unresolvable or the deploy poll has not run since the tick. Unit tests cannot see this because `pendingDeploy` is tested with `busy: true` from the caller only.
**Fix:** distinguish the two sources of `busy` in `evaluate()` — e.g. record `lastBusyForeign = !busy && lockIsBusy(nowMs)` and make `pendingDeploy()` return `false` when the busy came from a foreign lock (the loop then falls through to `fire()` → `aborted()`, which logs "lock held" and is bounded). If the F4 trade-off (tick N+1 must not run against a stale image after a foreign session merges) is judged to matter more, keep `wait-deploy` but log it honestly and start the `waitingSince` clock from `poll()` so the hour bound applies. Either way add a test where `evaluate({busy:false})` sees a fresh foreign lock and assert what `pendingDeploy()` answers.

**[minor] apps/chat/watch/advance-watcher.mjs:2101–2129 (headOf) — a real linked worktree yields `null`, so every loop from such a root stops on `no-progress` after two ticks**
`headOf` follows the `gitdir:` pointer but then looks for `refs/heads/<branch>` and `packed-refs` under that per-worktree directory. Real git keeps refs and `packed-refs` in the *common* dir (`<gitdir>/commondir` → `../..`), so the read fails and the function returns `null`, which `shouldContinue` counts as no progress. Observed against this repo: main checkout `headOf` === `git rev-parse HEAD`; `.worktrees/AS-95` → `headOf` returns `null` while git reports `61c2cb4`. The `head-worktree` unit test passes only because its in-memory layout puts the ref where real git does not. No production impact today (`repoRoot` is the main checkout) but the e2e recipe or any `ADVANCE_REPO_ROOT` pointing at a linked worktree would silently stop every loop after two ticks with a misleading reason.
**Fix:** after resolving `gitDir`, read `join(gitDir, 'commondir')` if it exists and resolve `refName` and `packed-refs` against that directory (relative to `gitDir`), keeping `HEAD` itself in `gitDir`. Rewrite the `head-worktree` fixture to the real layout (HEAD in the worktree dir, ref in the common dir) so the test can go red.

**[minor] apps/chat/watch/advance-watcher.mjs:1685–1690 (poll) — `blockedByLock()` is evaluated eagerly with side effects, so a message fire can be preceded by a contradictory log line**
`lockHeld: loopOps.blockedByLock()` runs on every poll, including the one where `decide()` returns `fire` over a dead-pid orphan lock. In that poll the log reads `LOOP-WAIT lock held by pid N (3s old); not firing the resumed loop over a tick that may still be running` immediately followed by `NOTE firing over stale lock: lock-stale-dead-pid` and a FIRE — two ticks beside each other after all (the message path is deliberately ungated, and that is documented, but the wait line is now false). Cosmetic, but the log is the board's evidence.
**Fix:** only consult `blockedByLock()` when `result.action !== 'fire'` (or pass a thunk and let `nextPollAction` call it after the message check).

**[minor] apps/chat/watch/advance-watcher.mjs:2342–2359 (resume) — a mirror already past the cap resumes and fires one tick before stopping**
`resume()` sets `pending = true` unconditionally; the cap (`ticks >= 24` or `elapsed >= 8h`) is checked only at settle. A watcher relaunched after a long outage with an `active: true` mirror from hours or days ago fires one full tick, then stops `cap-hit`. One tick's tokens, bounded, but avoidable.
**Fix:** in `resume()`, if `loop.ticks >= limits.maxTicks || now() - loop.startedAt >= limits.maxMs`, call `stop('cap-hit', …)` and `mirror()` instead of setting `pending`. One test: a stale mirror resumes to `active:false`, no fire.

**[minor] apps/chat/watch/README.md (AS-95 section) and the implementation report — two accuracy points**
(a) A human message arriving *between* loop ticks is fired by the loop path on the same poll `decide()` arms the debounce (`nextPollAction` returns `fire-loop` on `debounce`), so the 15 s burst-coalescing window does not apply mid-loop. That is a deliberate and reasonable choice (the test comment says so) but the README's "Rule (c) … the normal `decide()` → `fire()` path consumes the message" reads as if the debounce still applies. (b) The report says `makeLockOps` is "byte-identical to master"; `acquireLock` gained an `extra` parameter and a spread. Semantics of acquire/release/stale are unchanged and the tick's adoption rule in `.claude/commands/advance.md` step 0 matches `source`, `pid`, `nonce` individually, so the added `loop` key is harmless — but "additive, semantics unchanged" is the accurate claim.
**Fix:** one sentence in the README for (a); wording only for (b).

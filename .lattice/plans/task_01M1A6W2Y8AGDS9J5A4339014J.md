# AS-23: Chat UI — mobile-friendly responsive layout

Board request (chat DM @human:forrest, msg 163, 2026-08-30), verbatim: "Also,
I'm going to be using this on my phone so let's make it layout mobile
friendly". The board's primary interface with the company is this app, over
Tailscale, on an iPhone. Mobile is a first-class surface.

Planner: Owen Kessler (agent:cto-owen), 2026-08-30. Planned against master
with AS-19 merged (thread modal is the thread surface; the ≤600px full-screen
sheet already shipped there).

## Current state (what's already mobile-ready, what isn't)

Already done — do not redo:
- Viewport meta exists (`width=device-width, initial-scale=1`), index.html:5.
- Thread modal becomes a full-screen sheet at ≤600px (AS-19, style.css:158).
- Message bodies are `pre-wrap` + `break-word`; no fixed-width content in the
  main pane (`#main` has `min-width: 0`).

The five real gaps on a 390px viewport:
1. **Sidebar eats the screen.** `#sidebar` is `width: 240px; flex: none` —
   62% of a 390px viewport, permanently. The messages pane gets ~150px.
2. **Touch can't reach hover-gated actions.** `.message .actions` is
   `visibility: hidden` until `.message:hover` — there is no hover on a
   phone, so "reply in thread" is unreachable for messages with no replies
   yet. This is a functional break, not a polish item.
3. **iOS keyboard/viewport.** `#app { height: 100vh }` — on iOS Safari, 100vh
   overshoots the visible area (browser chrome), and when the on-screen
   keyboard opens, no CSS unit shrinks — the composer ends up hidden behind
   the keyboard. Separately, any input with font-size < 16px triggers iOS
   auto-zoom on focus (our base font is 14px), which both disorients and can
   leave residual horizontal scroll.
4. **Small touch targets.** Sidebar rows are `padding: 3px 16px` (~21px tall);
   action/close buttons are 12–16px text with no padding.
5. **`#task-panel` is `width: 300px` fixed** — fits a 390px screen but only
   just, and not a 320px one.

Plus the carried-forward AS-19 QA finding (Priya, review comment, backlog
item c): a text-selection drag that starts inside the thread dialog and
releases on the backdrop dispatches `click` on `#thread-modal` (the common
ancestor) and closes the modal mid-selection.

## Scope decision: the selection-drag fix FOLDS IN here (no separate task)

Rationale, recorded: (a) same three files this task already edits (app.js
wiring, thread-modal.js predicates, thread-modal.test.js); a separate task
guarantees a same-line merge conflict for zero coordination benefit. (b) The
trigger gesture — press-drag text selection over multi-KB prose — is *the*
canonical mobile selection gesture; on a phone it fires far more readily than
with a mouse. It is in-scope for "usable on a phone", not adjacent to it.
(c) It is ~15 lines including tests. Priya's sketched fix (pointerdown-target
check) is adopted as designed.

## Design

### 1. Sidebar becomes an off-canvas drawer at ≤700px

One mobile breakpoint for layout: **`@media (max-width: 700px)`**. (AS-19's
600px sheet rule is untouched — its threshold is about reading measure, this
one is about column layout; both fire on every phone. Do not "unify" them;
that would edit settled AS-19 CSS for aesthetics only.)

- Desktop (>700px): nothing changes. All new rules live inside the media
  query or `(hover: none)` blocks — the desktop cascade is untouched.
- ≤700px: `#sidebar` goes `position: fixed; inset: 0 auto 0 0; width:
  min(280px, 85vw); transform: translateX(-100%); transition: transform
  .2s ease; z-index: 26`. `#app.drawer-open #sidebar { transform: none; }`
- **Scrim:** new `<div id="sidebar-scrim" hidden></div>` in index.html (static
  markup, no user content — textContent rule untouched). Fixed, `inset: 0`,
  `rgba(0,0,0,.35)`, `z-index: 25`, `display: none` above 700px regardless of
  class. Shown/hidden in lockstep with the drawer class. Click closes.
- **Toggle:** new `<button id="sidebar-toggle" aria-label="Conversations">`
  first inside `#conv-header`, `display: none` by default, `display: block`
  at ≤700px, ≥40px hit area. Renders the ☰ glyph via markup text (static,
  not user content).
- **Z-order inventory** (documented so nobody re-derives it): dm-options 20 <
  scrim 25 < sidebar-as-drawer 26 < thread-modal backdrop 30 < task-panel 40.
  The drawer sits *below* the thread modal: a `t=` deep link at phone width
  shows the thread sheet on top, correct. dm-options (z 20, absolutely
  positioned inside `#sidebar`) joins the drawer's stacking context once the
  drawer is `position: fixed` + z-indexed, so it stays above the drawer's own
  content and below nothing that matters — no change needed.
- **JS wiring (app.js):** `openDrawer()` / `closeDrawer()` toggle
  `drawer-open` on `#app` and the scrim's `hidden` attr (house pattern).
  Close on: scrim click, and inside `selectConversation()` (any conversation
  pick — sidebar li, roster row, DM typeahead, new-channel — all funnel
  there; one hook covers all entry points). Drawer state is **view-local**:
  never touches the URL (AS-9 projection invariant — syncUrl/restoreFromUrl
  are not edited), never persisted, and the 5s poll's `refreshSidebar()`
  replaces list children *inside* the sidebar, so the open/closed class on
  `#app` is unaffected by re-renders.
- **Empty-state nicety:** in `init()`, after `restoreFromUrl('load')`, if no
  conversation is selected and the viewport is ≤700px (`matchMedia`), open
  the drawer once — a phone user lands on the channel list instead of a
  blank "Select a conversation" pane with a button they haven't met yet.

### 2. Touch reachability and target sizes

- `@media (hover: none) { .message .actions { visibility: visible; } }` —
  the hover-gate becomes always-visible exactly where hover doesn't exist.
  Desktop pointer behavior unchanged.
- Inside the ≤700px block: sidebar li / roster rows get `padding: 10px 16px`
  (≥40px rows); `.message .actions button`, `.thread-link`,
  `#thread-close`, `#task-panel-close`, `#sidebar-toggle` get padding for
  ~40px hit areas; composer Send buttons get `padding: 10px 16px`.
- **iOS zoom guard:** inside the ≤700px block, `textarea, input, select
  { font-size: 16px; }` — kills focus auto-zoom at the root cause.

### 3. iOS viewport + keyboard (the composer must stay visible)

- `#app`: `height: 100vh;` followed by `height: 100dvh;` (cascade fallback).
  Fixes the browser-chrome overshoot on iOS even before the keyboard enters.
- Keyboard: on iOS, *no* CSS unit (vh/dvh/svh) tracks the on-screen keyboard —
  only `window.visualViewport` does. Add a small pinned-height handler in
  app.js, active only when `window.visualViewport` exists: on `resize`, set
  `document.documentElement.style.setProperty('--app-height',
  visualViewport.height + 'px')` and counter iOS's automatic pan with
  `window.scrollTo(0, 0)`. CSS at ≤700px: `#app { height: var(--app-height,
  100dvh); }`. Result: the flex column shrinks to the visible area, the
  composer sits directly above the keyboard, `#messages` keeps its own
  scroll. ~12 lines, no library, no polling. Honest caveat: iOS keyboard
  behavior is only truly verifiable on the device — this is explicitly a
  board hand-walk criterion, and the code degrades to plain 100dvh where
  visualViewport is absent.
- Home-indicator clearance: add `viewport-fit=cover` to the existing viewport
  meta and `padding-bottom: calc(10px + env(safe-area-inset-bottom))` on
  `#composer`/`#thread-composer` inside the mobile block.

### 4. Global no-horizontal-scroll invariant

- `body { overflow-x: hidden; }` (top-level, cheap insurance — every pane
  already wraps; this pins the invariant against future content).
- `#task-panel`: `width: min(300px, calc(100vw - 32px))` (top-level rule
  replacing `width: 300px`; identical result at desktop widths).
- No new rule anywhere introduces a fixed width outside `min()`/media guards
  (QA greps for this, same as AS-19).

### 5. Thread-modal selection-drag fix (AS-19 QA backlog item, folded in)

- `thread-modal.js`: **add** a pure predicate; do not modify the two existing
  exports (their tests stay byte-identical):

  ```js
  export function shouldCloseOnBackdropGesture(clickEvt, downTarget) {
    // Close only when the gesture BEGAN on the backdrop too: a click whose
    // pointerdown landed inside the dialog is a text-selection drag, not a
    // dismissal. Null downTarget (no pointer event seen) falls back to the
    // click-target check alone.
    return isBackdropClick(clickEvt) &&
      (downTarget == null || downTarget === clickEvt.currentTarget);
  }
  ```
- `app.js`: on `#thread-modal`, a `pointerdown` listener records
  `e.target` into a local; the existing click handler switches from
  `isBackdropClick(e)` to `shouldCloseOnBackdropGesture(e, downTarget)` and
  clears the local after each click. No other wiring changes; Escape/×/
  popstate paths untouched.
- `thread-modal.test.js`: **additive** cases — down+click both on backdrop →
  close; down in dialog, click on backdrop (selection drag) → no close; null
  downTarget → legacy behavior (close). Existing test bodies unmodified.

## Test plan (honest about the harness boundary — same discipline as AS-19)

No browser harness exists; there is definitely no iOS harness. Three layers:

1. **Guarded suites, byte-unmodified:** `url-state.test.js`, `scroll.test.js`,
   and the *existing* tests in `thread-modal.test.js` must pass without
   modification (`git diff master...HEAD` empty for the first two; additive-
   only for the third). If any needs editing, the design drifted — QA flags.
2. **Container-assertable (new AS-23 test in api.test.js):** served HTML
   carries `viewport-fit=cover`, `id="sidebar-toggle"`, `id="sidebar-scrim"`;
   served CSS carries `@media (max-width: 700px)`, `translateX(-100%)`,
   `hover: none`, `100dvh`, `--app-height`, `overflow-x: hidden`,
   `safe-area-inset-bottom`, and zero occurrences of `width: 300px` as a bare
   rule. Full `node --test` suite green in-container.
3. **Hand-walk:** the board IS the mobile QA (his phone, over Tailscale, is
   the only real iOS device in the loop). Checklist below is written for him.

## Acceptance criteria

**Container/automated (QA verifies):**

A1. `node --test` fully green in-container; `url-state.test.js` and
    `scroll.test.js` byte-identical to master; `thread-modal.test.js` changes
    additive-only.
A2. The new AS-23 served-artifact assertions (test-plan layer 2) all pass.
A3. Desktop-invariance by inspection: every new CSS rule is inside
    `(max-width: 700px)` or `(hover: none)` blocks, except the three named
    top-level changes (dvh line on `#app`, `overflow-x` on body, task-panel
    `min()` clamp) — each a no-op at desktop widths.

**Board phone walk (~2 minutes, iPhone over Tailscale, after the live server
picks up the merge at next compose build/restart):**

B1. Open the chat. No sideways scrolling or pinch-zoom weirdness, in portrait
    or after rotating and back.
B2. The channel list is not squeezing the messages; on a fresh open with no
    conversation, the drawer greets you. Tap ☰ in the header — the drawer
    slides in; tap the dimmed area — it closes without changing anything.
B3. Tap a channel in the drawer — the drawer closes itself and the channel
    fills the width. Rows are comfortably tappable.
B4. Tap the message box. The keyboard opens and the box stays visible above
    it — no zoom-in jump, no hidden composer. Type and send; Send is easy
    to hit. Dismiss the keyboard; layout settles back.
B5. On any message, "reply in thread" is visible without any hover and
    tappable. The thread opens full-screen; reply from in there too (B4
    applies to the thread composer as well).
B6. In a thread with long text, long-press and drag a text selection that
    ends on the dimmed edge of the screen — the thread does NOT close.
    The × still closes it.
B7. Paste `/?c=board&t=113` into the phone browser — right channel,
    thread sheet open (AS-9 on mobile). Back button closes the thread.
B8. Glance at desktop after all this: nothing moved.

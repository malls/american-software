# AS-12: chat: harden assignmentsByActor against prototype-chain task fields

Found during AS-8 review (qa-priya, hostile-fixture attack; does not violate any AS-8 acceptance criterion — defense-in-depth backlog item). Two prototype-chain leaks in apps/chat/lib/lattice.js assignmentsByActor(): (1) the in-flight filter uses `task.status in IN_FLIGHT_RANK`, and `in` walks the prototype chain — a task JSON with status "constructor"/"toString"/etc passes the filter and renders as phantom work (verified in-container: status "constructor" appeared as 'AS-92 · constructor'; textContent rendering means no XSS, wrong data only). (2) the accumulator is a plain object, so `byActor[task.assigned_to] ??= []` with assigned_to "__proto__" reads Object.prototype (non-nullish) and the following .push throws TypeError (verified in-container). Server impact: /api/roster's try/catch swallows it, silently blanking the ENTIRE roster on one hostile task file; CLI 'chat roster' impact: unhandled crash. Trigger requires a hand-crafted .lattice/tasks/*.json (the lattice CLI never writes such values), hence low priority. Fix sketch: filter with Object.hasOwn(IN_FLIGHT_RANK, task.status), accumulate in a Map, return Object.fromEntries(map) (fromEntries uses CreateDataProperty so a '__proto__' key becomes a safe own property). Add regression fixtures: status 'constructor', assigned_to '__proto__'. Repro fixtures used in review are described here; rebuild from this description.

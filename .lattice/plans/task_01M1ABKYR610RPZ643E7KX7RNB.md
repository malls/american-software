# AS-25: Chat: push message delivery (websockets/SSE) — replace the 5s full-refetch poll

Explicit board request (Claude Code chat, 2026-08-30, under the amended explicit-request rule): 'we should switch to websockets for messages.' Motivation: the web UI polls 3 endpoints every 5s and refetches full conversation history each time — fine on loopback, laggy over the board member's Tailscale link from his phone (relayed DERP path, high RTT), and it worsens as history grows. Goal: server pushes new messages to connected clients instead of clients polling. Design considerations for the planner (decide, don't inherit): (1) zero-dependency constraint — a raw RFC6455 websocket server on node:http is nontrivial by hand; Server-Sent Events (SSE) is trivially zero-dep, auto-reconnecting, proxy-friendly, and one-directional server->client, which is all that's needed since sends already POST over HTTP — weigh SSE seriously before hand-rolling websockets; (2) the 5s poll also drives roster status and unread counts — decide what moves to push vs what stays on a slower poll; (3) visibility discipline: pushed events must respect AS-6 hidden-channel gating per connected identity (no #board frames to non-members — byte-parity thinking applies to the event stream too); (4) coordinate with AS-23 (mobile layout) and AS-19 (threads rework) — same files, sequence deliberately; (5) delta fallback: even with push, initial load + reconnect catch-up should use a since=<last-id> param instead of full history. Acceptance sketch: new message appears on a second connected client without polling; hidden-channel parity holds on the stream; poll cadence reduced or eliminated; suite green in-container.

# AS-76: Observability: design note — error tracking + product analytics posture for apps/invoicing and apps/chat (Sentry/PostHog; produces the board ask)

Board request (human:forrest, DM conversation 7, msg 521, 2026-09-03): "we need issues to set up posthog and sentry low priority but observability needs to be on the radar". This is the design task; the three instrumentation tasks (Sentry on apps/invoicing, PostHog on apps/invoicing, Sentry on apps/chat + watcher) depend on it and must not start until it is done.

WHY A DESIGN TASK FIRST, NOT STRAIGHT TO INSTRUMENTATION. Three things make this a decision rather than plumbing:

1. The stack decision (docs/engineering/01-stack-decision.md §11) already rules on this. Rule 3: any dependency that requires a hosted service, an API key, or registration of any kind is a board ask, no threshold. Rule 5: the suite must still run under --network none. Rule 4: transitive footprint is counted (the Sentry Node SDK carries an OpenTelemetry tree; PostHog's node SDK is smaller but not zero). And apps/invoicing/test/dependency-policy.test.js line 557 asserts that no app source outside the Stripe client module contains an outbound HTTP client — a Sentry/PostHog SDK dropped into the app fails that guard by construction. The design has to say how a second (and third) egress channel coexists with the chokepoint rule: the default answer to evaluate is one egress module per external service, each with its own chokepoint test, mirroring lib/stripe.

2. Data handling. apps/invoicing holds freelancer credentials, client names and emails, contract text, and invoice mirrors (amounts, line items, Stripe ids). An error-tracking payload that captures request bodies or local variables, or an analytics event that carries invoice contents, moves that data to a third party. "Never in the flow of funds" is a custody constraint on money, but the same instinct applies here: an analytics pipeline that mirrors invoice contents is a data-handling decision, not a plumbing one. The design must produce an explicit allow-list of what leaves the machine (event names, hashed/opaque ids, error type + stack, app version) and a deny-list (PII, amounts, line items, contract text, session tokens, Stripe ids), and say how the deny-list is enforced by a test, not by review discipline. Sentry's beforeSend / PostHog's property sanitisation are where this lands if SDKs are used; a hand-rolled egress module makes it a schema.

3. Self-hosted vs cloud changes what the board ask IS. Cloud Sentry / cloud PostHog: an account (free tier), a DSN/API key, and product data resident with a vendor under their DPA. Self-hosted: no vendor DPA question, but a Digital Ocean droplet (spend) and an ops surface we own — PostHog self-hosted in particular is a multi-service deployment. Either path is board-gated (see below); the design decides which one to ask for and why.

SCOPE OF THE DELIVERABLE: a written design note at docs/engineering/04-observability-posture.md covering (a) what is instrumented on which surface and why the two apps differ (invoicing is the product with real users; chat is internal tooling whose only users are employees and the board — product analytics there is meaningless, error tracking has modest value mainly for the headless watcher whose failures have historically been silent, see AS-21); (b) SDK vs raw ingest API — both Sentry (envelope endpoint) and PostHog (/capture, /batch) accept plain HTTP, so a zero-new-dependency egress module using node fetch is a live option that sidesteps rules 4 and 5 entirely; the note measures the transitive footprint of the SDK route per rule 4 before choosing; (c) the data allow/deny-list above and its enforcing test; (d) self-hosted vs cloud with the cost/ops tradeoff stated; (e) the exact board ask, written as one scannable needs_human comment, ready to file. Time-box: one planning-stage session; default answer if the box expires: raw ingest via a fetch-based egress module, cloud free tier, deny-list enforced by a schema test, ask filed for both vendors at once.

BOARD GATE (non-negotiable, from CLAUDE.md product section): every external service signup is board-gated, including free and test-mode accounts. This task creates NO accounts, requests NO keys, sends NO data anywhere. It PRODUCES the ask; the ask is filed as a separate needs_human item when this task closes. Rationale for deferring the ask rather than filing it now: AS-51 (Stripe test-mode account) is already parked on the board's desk, and the observability ask cannot be written honestly until self-hosted vs cloud is decided — a cloud ask is "approve two free accounts", a self-hosted ask is "approve a droplet". Asking before knowing which would be asking the board to do the design.

PRIORITY: low, per the board's own words. Does not jump the D1 line (AS-45/46/47/48/49/50/70) or the chat cluster (AS-27, AS-75, AS-28, AS-73, AS-74, AS-72, AS-61). Sequencing recommendation: pick this up when an implementer lane is idle; the Sentry-on-invoicing task should land before the first non-employee user touches the product (an error we cannot see is one we cannot fix), PostHog-on-invoicing after there are users to measure.

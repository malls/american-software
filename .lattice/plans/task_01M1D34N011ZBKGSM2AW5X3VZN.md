# AS-38: D1 v1: Stripe client wrapper with custody guard (never in the flow of funds)

Spine task 3 of D1 v1, and the mechanism behind a standing company constraint rather than a feature. Build the single module through which EVERY Stripe API call in this product passes. It must: hard-require the Stripe-Account: acct_... header on every connected-account call; reject at the call site any request carrying transfer_data, on_behalf_of, or platform-side charge/invoice parameters; expose a transport seam so tests can substitute a fake; and ship tests that FAIL IF THE BAN IS REMOVED (assert the guard's refusals, not only the happy path).

IMPLEMENTS: docs/engineering/00-d1-v1-milestone-plan.md section 3 row C-03 (IN by mandate — board constraint 7 and assumption A3, milestone plan section 5). Section 8.3 spine task 3.

DECISION CONTEXT. This is not defensive-coding taste. docs/strategy/03-gate-verdicts.md constraint 7 says we are never a payee, never an aggregator, and never in the flow of funds. The D1 spike (docs/strategy/spikes/spike-D1-freelancer-invoicing.md section 1) MEASURED that the forbidden shape lives in the same API and that stripe-mock accepts it: a platform-side invoice with transfer_data[destination] is a perfectly valid Stripe call that silently makes us merchant of record and puts client money on our balance. The API will not hold this boundary for us. This module is how we hold it mechanically instead of by memory, and it lands BEFORE any code that calls Stripe — the only ordering under which the "permanent design-review obligation" the spike priced means anything.

Second reason for the chokepoint (assumption A2): the board has not ruled whether a Stripe application fee is clean under constraint 7 (docs/strategy/07-decision-memo.md section 4.2; docs/strategy/08-board-decision.md section 3.2 makes subscription-only the operative default). BUILD NO APPLICATION-FEE PATH — the constraint is honoured literally. Routing every call through one module is what makes a future board reversal one parameter on one call rather than a refactor. Declining to foreclose is not the same as building.

VERIFICATION: unit tests against the fake transport, plus request-shape validation against stripe-mock (MIT, free, no account — run it as a compose service from its public image; pulling a public image is not a signup and not a purchase). Tests must include negative cases: a call without Stripe-Account is refused; a call carrying transfer_data or on_behalf_of is refused; deleting the guard turns the suite red. Runnable now with no accounts.

NOT IN THIS TASK: any product endpoint or feature that uses the wrapper; webhook signature verification (that belongs to the webhook task, which has different inputs and a different failure mode); any real Stripe account or network call — none exists and none is assumed.

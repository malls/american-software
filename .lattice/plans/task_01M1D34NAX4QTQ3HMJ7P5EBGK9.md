# AS-41: D1 v1: Stripe Connect onboarding (server) — account, account_links, return/refresh, readiness

Chain link 2, "connects their own Stripe account" — server side only. Create the connected account with POST /v1/accounts (bare Standard-equivalent defaults), mint hosted onboarding links with POST /v1/account_links (type=account_onboarding), handle the return_url and refresh_url routes, and maintain the connected account's readiness state (charges_enabled plus outstanding requirements) on the record the data-model task defines.

IMPLEMENTS: docs/engineering/00-d1-v1-milestone-plan.md section 3 rows C-10 (Connect account creation and hosted onboarding) and C-11 (readiness state gating invoicing). Both IN under Rule 1.

DECISION CONTEXT. Every call goes through the custody-guard wrapper — no direct HTTP, no exceptions. The D1 spike (docs/strategy/spikes/spike-D1-freelancer-invoicing.md section 1) verified these exact primitives and that a bare POST /v1/accounts yields the Standard-equivalent controller properties we want: losses.payments=stripe, fees.payer=account, requirement_collection=stripe, stripe_dashboard.type=full. Stripe bears payment-loss liability, the freelancer pays Stripe's fees, and STRIPE COLLECTS KYC — we never see identity documents or bank details. That is precisely why building our own identity/document collection is OUT (row C-13, Rule 2), and it is a large part of why this architecture is constraint-7 clean.

Readiness matters because Stripe returns the user through return_url whether or not their requirements are complete. Invoicing an account that cannot charge breaks chain link 4, so the readiness flag maintained here is the gate the invoice task reads before finalizing.

VERIFICATION: request and response shapes validated against stripe-mock (free, no account); the return/refresh route logic and the readiness state machine unit-tested against fixture account and account.updated payloads. NAMED RESIDUAL, stated at creation rather than discovered at the review gate (milestone plan section 8.2, right-sizing test 3): stripe-mock is stateless and cannot exercise the real hosted-onboarding round trip, and it is not confirmed that Stripe test mode accepts http://localhost return/refresh URLs. Both are settled by the test-mode acceptance run, which is gated on the board's Stripe test-mode account. If localhost URLs turn out to be rejected, that acceptance task files a new board ask for local ingress — this task opens nothing and assumes no account exists.

NOT IN THIS TASK: the Connect screen and its states ledger (the onboarding-UI task); webhook receipt infrastructure (the webhook task — this task defines how an account.updated payload changes readiness, the webhook task delivers it); anything touching invoices.

# AS-24: chat CLI on host writes to a DB view the container server never sees — route CLI writes through the server API or fail loudly

Observed live this tick (2026-08-30, ~20:5xZ). Read-path WAL staleness under the macOS Docker bind mount is known (ticks missed the message that fired them); this is the WRITE-path twin, verified: 'node apps/chat/bin/chat.js dm human:forrest ...' on the host reported success as message id 161 — but GET /api/messages?conversation=7 never showed it, and the server later assigned ids 165+ in the same conversation. The host CLI wrote into a stale host-side WAL view of apps/chat/data/chat.db that the containerized server does not share; the write is silently invisible (and id 161 may resurface as an orphan/duplicate after a checkpoint — check for it during fix verification). Impact: any host-side CLI write (dm, post, read) can silently fork the DB — worse than the read bug because it loses outbound board communication. Workaround used this tick and until fixed: all writes via the server HTTP API (POST /api/messages, /api/read, /api/dms). Fix direction for the planner (not binding): make bin/chat.js talk to the server API when the server is up (it is the single writer), or refuse to touch the DB file directly when a server lock/container is detected — silent success is the failure mode to remove.

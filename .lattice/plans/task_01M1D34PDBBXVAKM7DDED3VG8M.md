# AS-50: D1 v1: recorded acceptance run against Stripe test mode (v1 done)

Planner: cto-owen (2026-09-12). Complexity: medium. Implementer: **developer-marcus**. Reviewer: **qa-priya** (Ruben if she is mid-cycle when review opens). Milestone plan §3 C-06, §6.1.

## 1. Scope

One recorded run of the loop on the local compose stack against the board's real test-mode account, driven by a host-side script wherever a tick can act and by the board at a browser only where Stripe's hosted pages require a human. The record commits under `docs/engineering/`. Every divergence from the stateful double (AS-49) is listed with a disposition. Live mode, deployment, and opening any account stay OUT.

**Why no board ask up front.** Webhook delivery uses `stripe listen` under the SAME account — explicitly part of ask A1, which the board satisfied (AS-51). Return/refresh URLs are `http://127.0.0.1:8348/...` (config default); Stripe's documented rule is HTTPS in live mode only, and the board's browser is on the host that publishes 8348. **Contingency, pre-committed:** if `POST /connect-stripe/start` answers 502 because Stripe refused the `return_url`, the driver STOPs, the record captures the error body, the implementer files "Board ask: local ingress for hosted-onboarding return URLs" (`--actor agent:developer-marcus`, high), links `AS-50 depends_on` it, and AS-50 → `blocked`. No tunnel, no proxy, no workaround.

## 2. Approach: a resumable, three-phase driver with two human gates

`apps/invoicing/acceptance/run.mjs` (host-only, zero deps, the `capture.mjs` convention; never inside the image). Persisted state in `apps/invoicing/acceptance/state/` (gitignored). Every phase is idempotent and re-runnable; `node acceptance/run.mjs <phase>` from `apps/invoicing/`. Binaries by absolute path (`docker` from `apps/chat/data/deploy-state.json` `dockerBin`; `/opt/homebrew/bin/stripe`).

**Secrets discipline (hard):** the driver reads `.env.local` into memory only, passes the key to `stripe`/compose via child env, never prints, logs, or writes a key or the `whsec_`; the state file stores only a SHA-256 of the signing secret (rotation detection). Redaction runs on every byte written under `docs/` (§4). The board's `.env.local` is never modified.

**Phase 1 — `up` (tick, Marcus's implementation tick):** (a) start the **relay** on `127.0.0.1:8352` (refuse if held): a ~40-line http server that forwards each request's raw `Buffer` and `stripe-signature` header byte-for-byte to `127.0.0.1:8348/webhooks/stripe`, then appends `{receivedAt, forwardedMs, eventId, type, account, created, status, body, bodySha256, rawEvent}` to `state/deliveries.jsonl`; (b) spawn `stripe listen --forward-to http://127.0.0.1:8352/webhooks/stripe --forward-connect-to <same>` detached (pid file, log with the secret line redacted), parse the `whsec_` from its Ready line; (c) `docker compose up --build -d web` with both secrets in the child env; assert the boot line shows both as `[redacted]`; (d) `POST /signup` a throwaway freelancer (generated password, stored in state); `GET /` with the cookie → 200; (e) write `state/run.json` `{phase:1, freelancer, cookieDigest, listenerPid, relayPid, apiVersion, cliVersion}`, print the board's instructions (§3 gate A). The 303 from a driver-side `POST /connect-stripe/start` is **not** used for onboarding (links are single-use and short-lived; the board mints his own at the button) — it is used only to verify the URL family is `connect.stripe.com` and that `/v1/accounts` + `/v1/account_links` succeed for real.

**Gate A (needs_human):** the board signs in at `http://127.0.0.1:8348/signin` with the throwaway credentials, presses Connect Stripe (screen 2), completes Stripe's test-mode onboarding using its test-data shortcuts [UI may differ], lands back on screen 2 READY, and replies with (1) "done" and (2) the email address to use as the test client — one inbox he can read. He types no key material anywhere.

**Phase 2 — `issue` (tick):** verify readiness by **push** (`account.updated` in `deliveries.jsonl` → `ok: readiness`) and by **pull** (driver `GET /connect-stripe/return` → 303; screen 2 `data-state` READY); then, over the API routes, in E1's order: client (the board's email) → contract → draft (E1's two line items, 12,500 usd, 30 days) → `/finalize` → `/send`. Save screens 3 and 5 HTML. Print gate B. The relay's in-window probes fire automatically on the first handled `invoice.*` delivery: replay identical bytes+header → expect `duplicate`; replay with one hex char of `v1` flipped → expect 400.

**Gate B (needs_human):** the board checks the client inbox for Stripe's invoice email (arrived / not, sender, subject, minutes after send), opens the hosted invoice page (from the email, or the URL copied from screen 5 in his signed-in browser), pays with `4242 4242 4242 4242`, and replies. The tick's DM states the listener is alive (pid, started at) before asking.

**Phase 3 — `verify` (tick):** mirror `paid` on screen 5 (`data-state` `S5-DEFAULT-PAID`) and screen 3; `invoice.paid` → `applied` in the log; tolerance probe (replay the genuine paid delivery, now > 300 s old → 400); custody reads via the CLI in read-only verbs (`invoices retrieve in_…` with and without `--stripe-account`; `balance_transactions list --limit 3` on the platform); divergence computation (§4); write the record; regenerate; leave the stack up for review. Teardown at merge: `docker compose down -v` (the acceptance database holds the board's email).

## 4. The record's structure and the divergence rule

Sections, in order: (1) outcome in one sentence + date + master commit + Stripe API version + CLI version; (2) preconditions (key-shape check citation, boot line, listener session, relay port); (3) expected-vs-observed table, one row per E1 step (route, expected status/Location/calls from AC-2..AC-14, observed, ms); (4) delivery log table in receipt order (event id, type, `account`, `created`, latency, app status + outcome) — ignored types included; (5) the board's two turns, quoted verbatim from chat; (6) probes; (7) divergences from the double; (8) unmeasured/remaining. **Redaction:** client email → `[client-email]`; freelancer email → `[freelancer-email]`; the path/token of `hosted_invoice_url` and `invoice_pdf` → `…/[token]`; any `whsec_`/`sk_`/`pk_` prefix → refuse to write (throw). Test-mode ids (`acct_`, `cus_`, `in_`, `evt_`) are kept. **Divergence = mechanical:** for each handled type observed, `data.object` top-level keys, `status_transitions` keys, and `requirements.*` keys vs the double's fixture (R3); event ordering vs E1's sequence; any outcome other than the expected one (an `unknown-target` for an early `invoice.created` is expected to appear — record it, do not hide it). Each divergence gets a disposition: fixed in this branch (behaviour, small) / filed by the orchestrator at merge (behaviour, not small) / accepted by design with the reason. The two AS-49 planner notes (R4 conflict-then-duplicate; Q5 expected column) are addressed in (7) and (3).

## 6. Acceptance criteria (each names its falsifier; red must be observed, not argued)

- **AC-1** Boot line and `/healthz` show `stripeSecretKey` and `webhookSecret` as `[redacted]` before any step; the driver refuses to proceed otherwise. *Falsifier:* bring `web` up without the secrets env (a one-off on another port, `--base`) → the driver STOPs at precondition, state file untouched.
- **AC-2** Phase 1 completes: signup 303 → `/`, driver-side connect start answers 303 to a `connect.stripe.com` URL, `run.json` written. *Falsifier:* AC-1's keyless one-off → `/connect-stripe/start` 503 → `STOPPED at step …`, exit 1.
- **AC-3** Readiness lands by both paths: `account.updated` delivery with `ok: readiness` in the log AND a driver pull → screen 2 `data-state` READY; both before any invoice call. *Falsifier:* gate A not yet done → phase 2 refuses at readiness with the two observed states named, zero invoice calls.
- **AC-4** Finalize → mirror `open`, `amountDueMinor` 12500 = `totalMinor`, `hosted_invoice_url` present on screen 5; send → `sentAt` set; the `invoice.sent` delivery answers `fields` or `stale` (recorded which). *Falsifier:* a second `/finalize` after `open` makes no Stripe-visible change (no new `invoice.created` delivery arrives; the E1 skip rule holds against real Stripe).
- **AC-5** Relay transparency: every genuine delivery of a handled type answers 200 with a non-error outcome. *Falsifier (in-window tamper):* the same bytes with one hex char of `v1` flipped → 400 `SignatureError: verify-signature`; screen 5 unchanged.
- **AC-6** Exactly-once: the in-window identical replay → 200 `duplicate`, screen 5 byte-identical before/after. *Falsifier:* the replay is the red for a receiver that re-applies; observed body must be `ok: duplicate`, not `applied`.
- **AC-7** Tolerance is real: the genuine paid delivery replayed > 300 s later → 400. *Falsifier:* this IS the red; a 200 here is a finding.
- **AC-8** Paid: after gate B, `invoice.paid` → `applied`; screen 5 `S5-DEFAULT-PAID` with `paidAt`; screen 3 lists it paid. *Falsifier:* if the listener died between ticks, phase 3 reports the gap (pid dead, no `invoice.paid` row) and the recovery is a fresh invoice through gates B again with the listener confirmed up — recorded as a divergence, never patched by hand.
- **AC-9** Never in the flow of funds, observed: `invoices retrieve in_…` WITHOUT `--stripe-account` → `resource_missing`; WITH it → `paid`; platform `balance_transactions list` → 0 rows after payment. *Falsifier:* the platform-scope retrieve succeeding is the red.
- **AC-10** The driver's CLI helper allows only `listen`, `invoices retrieve`, `balance_transactions list`, `events list`; anything else throws before spawn. *Falsifier:* reviewer calls it with `invoices pay` → refusal, no process spawned.
- **AC-11** Redactor: the committed record and directory contain zero matches for `whsec_|sk_test_|sk_live_|pk_`, the client email, or a hosted-invoice token (grep counts in the review). *Falsifier:* feed the redactor a line containing `whsec_x` → it throws; a line with the client email → `[client-email]`.
- **AC-12** Suite green under `--build` after the `SKIPPED_DIRS` change; the demo-import guard extended. *Falsifier:* an `import '../acceptance/run.mjs'` added to a scratch copy of `routes/pages.js` → dependency-policy red.
- **AC-13** Record §7 lists every divergence with a disposition and §3 has one row per E1 step (count = 13 rows, AC-2..AC-14 of AS-49). Floor check: reviewer counts rows and dispositions.

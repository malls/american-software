# AS-56: design tokens: danger-solid on bg-surface (dark) is 2.97:1 against the 3:1 non-text floor — palette amendment, now inherited by two consumers

Planner: designer-sofia. Complexity: medium (confirmed — see §6).

## 1. The decision

**Retune `--color-danger-solid`'s dark-mode value** (option (b) from the CTO's
routing comment: "re-tuning danger-solid's dark value if a window exists").
Add one new primitive step to the existing `danger` ramp — `danger-400`,
generated by the documented method (§11: same hue 355°/sat 68%, new
lightness step, never hand-picked) at **L=50 → `#D62937`** — and re-point the
dark-mode `--color-danger-solid` alias from `danger-500` (`#CE2735`) to
`danger-400` (`#D62937`). `--color-danger-solid-hover` (dark: `danger-600`,
`#AB212C`) is untouched. Light mode is untouched (already clears every floor
below).

Method: standard HSL(355°, 68%, L) → sRGB → WCAG 2.1 relative-luminance
contrast, per BRANDING.md §11 exactly (script in
`scratchpad/agent-designer-sofia/AS-56/contrast.mjs`, kept for the record —
not part of the deliverable). Computed, not estimated.

### Measured ratios (dark mode)

| Pair | Old (`danger-500`, `#CE2735`) | New (`danger-400`, `#D62937`) | Floor | Result |
|---|---|---|---|---|
| `danger-solid` boundary vs `bg-canvas` (non-text) | 3.46:1 | **3.69:1** | 3:1 | PASS (unchanged verdict, ratio moves) |
| `danger-solid` boundary vs `bg-surface` (non-text) — **the named failure** | 2.97:1 | **3.17:1** | 3:1 | **FAIL → PASS** |
| `danger-solid` boundary vs `bg-surface-sunken` (non-text) | 2.35:1 | **2.51:1** | 3:1 | FAIL → FAIL (improved, not closed — carried forward, §2) |
| `text-on-danger` (white) on `danger-solid` | 5.30:1 | **4.96:1** | 4.5:1 | PASS (unchanged verdict, margin shrinks from 0.80 to 0.46) |

Light mode: no value changes, no ratio changes, all rows already PASS
(unaffected by this task — confirmed by direct computation, not assumption:
`danger-solid` boundary vs light `bg-canvas`/`bg-surface`/`bg-surface-sunken`
are 6.63/7.03/6.28, all comfortably above 3:1).

### The AS-29 F2 claim, tested explicitly

F2 states: "no single danger colour clears both a 4.5:1 white label and 3:1
as a border on all dark surfaces." A full lightness sweep at hue 355°/sat 68%
(30 ≤ L ≤ 62, step 1, see `scratchpad/agent-designer-sofia/AS-56/contrast.mjs`
output) shows:

- `bg-surface-sunken` only clears 3:1 at **L ≥ 57** (`#DC4753`, 3.00:1).
- White-on-fill only clears 4.5:1 at **L ≤ 54** (`#D93A47`, 4.52:1).

These two windows are disjoint (57 > 54) — **the broad claim, "on all dark
surfaces," holds: the window is empty.** No single dark value for
`--color-danger-solid` can pass both `bg-surface-sunken` and the white-label
floor simultaneously.

But the two actual consumers (reference.css:428 and the AS-30 wireframes)
only ever pair this token with `bg-surface`, not `bg-surface-sunken` — and a
third, real consumer this task's routing comment didn't name also only pairs
it with `bg-surface` (§3, `apps/invoicing/public/app.css:214`). Restricted to
that pairing, the window is **`L ∈ [49, 54]`** — non-empty. L=50 was chosen
near its center for roughly even margin on both floors (surface: +0.17 over
3:1; white: +0.46 over 4.5:1) rather than hugging either edge.

**Why this stays on-brand:** `danger-400` is generated from the exact hue and
saturation every other danger step uses (§3.1's own extension rule), sits
between the existing `-300` and `-500` steps in the ramp, and is not a new
hue, saturation, or family — it is the ramp filling in a step it happened not
to need before.

### Why not a split token (option (a))

A dedicated non-text `danger-border` token (decoupled from the white-label
constraint) *would* clear all three dark backgrounds at once — e.g. reusing
the existing `danger-300` (`#E5767F`, already shipped as dark `danger-text`)
scores 6.30/5.42/4.28 against canvas/surface/sunken, all comfortably >3:1,
with zero new hex values. That option was seriously considered and rejected
for v1, not because it doesn't work, but because of what it would require:
introducing a new semantic token means editing the two docs consumers *and*
the real product consumer (`apps/invoicing/public/app.css:214`), all with
identical mechanical risk to the retune, for a benefit (closing the
`bg-surface-sunken` row too) that no shipped consumer currently needs. The
retune is a strict subset of that work — one token, zero new call sites,
same files touched for the generated artifacts — and fixes the one row
anyone actually renders. If a future consumer needs a danger-toned
non-text boundary on `bg-surface-sunken`, option (a) is the v2 answer;
recorded below as a v2 candidate, not built now (time-box discipline).

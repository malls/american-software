# /advance — one company tick

You are the operating loop of The American Software Company. Read `PHILOSOPHY.md` and `CLAUDE.md` before acting. One invocation = one bounded tick of the company. There is no human prompt beyond this command; the company acts on its own judgment, within the rules.

## Tick procedure

0. **Take the single-flight lock.** Atomically create `apps/chat/data/advance.lock` (write `{"pid": <holder pid>, "startedAt": "<ISO now>", "source": "loop"|"manual"}` with the `wx` flag). **The pid must belong to a process that stays alive for the whole tick (learned 2026-09-09):** the Bash tool's shell exits when each command returns, so a lock written with `$$` is dead-pid the moment it exists and the watcher's `lockIsBusy()` correctly treats it as stale — it stole such a lock and deployed 8347 under a live tick at 21:46Z that day, and every loop-session lock since 2026-09-03 had been stealable the same way. In a live session, create the lock FROM a background holder process that writes its own pid and keeps running: `node -e '<create with wx using process.pid; setInterval(rewrite startedAt, 20 min); exit when the file is gone or not ours>'` launched with `run_in_background`. That one process is both the owner and the heartbeat; it exits by itself when the tick removes the lock. If it already exists and is fresh (owner pid alive AND `startedAt` < 75 min old), **end the tick immediately as a no-op** — another tick is running and its inbox sweep will deliver any pending messages. If it is stale (dead pid or > 75 min), delete it, log the steal in your tick output, and take it. (Tick timeout 60 min, staleness 75 — both moved 2026-09-11 from 30/45; `CLAUDE.md` § Operating modes.) **Lock holders must heartbeat:** a tick or loop that holds the lock across long sub-agent work MUST rewrite the lock with a fresh `startedAt` at least every 30 minutes (same pid/source/nonce, new timestamp) — an unrefreshed lock past 75 min is legitimately stealable, and the company has lived the resulting duplicate-work collision once (2026-08-31, duplicate CEO scoring pass; see docs/strategy/04-scores-ceo.md Drafting record). **Watcher-fired ticks (AS-7/AS-15/AS-20/AS-16):** a watcher-fired tick receives `watcher:<pid>:<nonce>` as this command's argument (the watcher spawns `claude -p '/advance watcher:<pid>:<nonce>'`; the nonce is 16 hex chars, minted fresh per fire and written into the lock the watcher took). Adopt the existing lock as YOUR lock only when **all three** hold: `lock.source === "watcher"` AND `lock.pid` equals the marker pid AND `lock.nonce` equals the marker nonce — your parent watcher took it before spawning you. Then proceed with the tick, and do NOT release it at tick end: the watcher releases its own lock in `settle()` when the tick exits. Anything else — wrong source, pid mismatch, nonce mismatch, nonce **missing on either side** (no legacy grace for old-format locks or markers), or no argument marker at all — is a foreign lock: end the tick as a no-op (or steal it if stale, per the staleness rule above, which is nonce-blind). No env read is needed for this check — the argument is the contract (`ADVANCE_TICK_PARENT`, same `watcher:<pid>:<nonce>` format, is set as a belt for contexts where env is readable; headless ticks cannot read env vars).
1. **Assess state.** Run `lattice list` across statuses, scan the `needs_human` queue, check `git status`/`git log` for sibling-agent work in flight (shared worktree discipline applies — never touch changes you can't attribute), and **sweep the chat inbox with the chat CLI — it self-routes (AS-24).** `node apps/chat/bin/chat.js` probes the server and proxies every read and write through the HTTP API whenever a server is reachable; it refuses loudly (exit 1, zero side effects) when the probe is ambiguous, and opens the DB directly only when nothing is provably listening. Host-side WAL divergence (stale reads that missed the triggering message; the orphan-161 write) is enforced away, so use the CLI directly: for each active employee identity (from `personnel/` frontmatter), `chat inbox --me <identity>` (or `chat channels --me <identity> --json` for unread counts). Fallback only — if the CLI itself is unavailable, the raw API still works: `http://127.0.0.1:8347/api/conversations?me=<identity>` for `unread > 0`, bodies via `/api/messages?conversation=<id>&me=<identity>` — e.g. `node -e` with `fetch` (curl is not in the tick allowlist). Never read host sqlite while the server is up; never override an AS-24 refusal with `CHAT_MODE=direct` during a tick.
2. **Pick ONE highest-leverage action**, in rough priority order:
   - An unread board-member (`human:*`) message addressed to an employee → spawn that employee to read their inbox and respond. **Ack first (CLAUDE.md norm):** the employee's first tool action after reading is a one-line reply saying what they'll do — before any Lattice writes, planning, or sub-agent work; the substantive follow-up reply comes after the work. Resulting work becomes Lattice tasks created by that employee (`--on-behalf-of human:forrest`); if a task already covers the request, they say so in their reply and reprioritize it if warranted.
   - A task in `review` → run the QA review stage (fresh-context QA employee) against the task branch diff (`git diff master...feat/AS-<n>-<slug>`), working inside `.worktrees/AS-<n>/`. **PR discipline (board directive DM msg 576, narrowed by the board in Claude Code chat 2026-09-07: only what the board is asked to review gets a PR).** No PR is opened at `review` by default. The moment a tick asks the board to look at code — a merge held for the board, a `needs_human` on a diff, a safety-valve override — the owning employee pushes the branch (`git push -u origin feat/AS-<n>-<slug>`), opens the PR (`gh pr create --base master --head feat/AS-<n>-<slug> --title "AS-<n>: <task title>"`, body = what/why, plan path, acceptance criteria), posts QA's verdict comment to it with `gh pr comment` (findings first, sweep second), and puts the PR URL in both the Lattice comment and the chat message; later rework commits push to the same branch. The board answers in chat or on the PR; **the merge stays local** — never `gh pr merge` or the GitHub button. On pass: from the MAIN checkout, merge `--no-ff` into master; **then the records step, gated on the deploy (resumed at the AS-91 merge, 2026-09-09):** run `./apps/chat/chat export` only when `apps/chat/data/deploy-state.json` shows `runningId` equal to `desiredId` — the CLI runs against the container, and an export taken while the container still runs pre-merge code re-emits exactly what the merged guard forbids; if they differ, defer the export to the next tick and say so in the report. When it runs and changes `apps/chat/data/export/`, commit those files alone as `records: chat export <YYYY-MM-DD>` (CLAUDE.md § Git methodology, "Records step"); push master (GitHub marks any PR merged); `git worktree remove .worktrees/AS-<n>`; delete the branch locally and, if it was pushed, on origin (`git push origin --delete feat/AS-<n>-<slug>`); move to `done` — then, if the merge touched `apps/chat/` image inputs, read `apps/chat/data/deploy-state.json`: the watcher deploys within ~60 s on its own (AS-75), so say nothing when `dockerBin` is non-null and the watcher heartbeat is fresh. If either is false, tell the board in the merge reply that the chat deploy will **not** happen unattended and name the reason from that file. (Deliberately not a deploy step: the mechanism is the watcher's, and a step that duplicates it would deploy twice or claim a deploy that did not happen.) **Hosted artifacts:** if the merge changed an input of a published artifact (`BRANDING.md`/tokens → brand-artifact; `docs/design/wireframes/` → wireframe-artifact; `docs/demo/d1/` → d1-demo-artifact), the orchestrator runs that skill's publish step in the same tick — the `Artifact` tool is in the tick's grant set (2026-09-12). If the tool turns out to be unavailable headless, say so once in the report and leave the republish to the next live session; never say it was republished when it was not.
   - A task `planned` or `in_progress` → run or continue the implementation stage: code + tests commit on the task branch INSIDE its worktree (`.worktrees/AS-<n>/`); board state (status, comments) commits to master from the main checkout. A `complexity: low` task skips the separate planning stage: one `developer-*` writes the plan, commits it to master, creates the branch and worktree, and implements in the same stage (CLAUDE.md § Lifecycle, "Scaled by complexity"). QA review is never collapsed.
   - A task in `in_planning` → run the planning stage: write the plan file and commit it to MASTER (plans are board state), then create `feat/AS-<n>-<slug>`, `lattice branch-link` it, and `git worktree add .worktrees/AS-<n> feat/AS-<n>-<slug>`.
   - Backlog has tasks but nothing in flight → pull the most important one into the lifecycle (`lattice next --claim`).
   - Backlog is empty → act as the cofounders: decide what the company needs next. Create engineering backlog tasks with decision context baked into descriptions, or advance non-engineering work (hiring, strategy, legal, marketing — recorded in `CLAUDE.md`/docs per the scope rules, never in Lattice).
   - The action requires a job title that doesn't exist → hire: write the personnel file under `personnel/`, record the hire date, MBTI, and resume per `CLAUDE.md`.
3. **Execute via employees.** Every action is performed by a named persona employee whose job title matches the work. Lifecycle stages get fresh-context sub-agents per the Employee Execution Model in `CLAUDE.md`. Every Lattice operation uses `--actor agent:<employee-id>`. Employees leave comments as they contribute — within the length caps in `CLAUDE.md` § Lifecycle, "Breadcrumbs" (a comment ≤ 300 words; logs and battery output go in the actor's scratchpad). **Every `→ planned` and `→ review` transition carries `--no-auto-review`**; a daemon flag that appears anyway is cleared with `lattice needs-human <task> --clear --note "<which qa-* review covers it>"` — never left standing, never asked of the board. **Model fallback:** when Fable refuses a spawn for usage, re-invoke the same employee on Opus at once and name it in the report. **Company events (AS-100).** Tick start and end are recorded by the watcher; the orchestrator never emits `tick_*`. At each stage boundary the orchestrator runs the emit CLI as a plain top-level Bash command — never inside `$(…)`, a pipeline, or a compound command, which the headless permission layer denies (AS-92) — with `--actor` set to the orchestrating employee and `--employee` to the employee doing the stage:
   - **Before spawning a stage's employee:** `node apps/chat/bin/events.js emit stage_started --task AS-<n> --stage plan|implement|review --employee agent:<employee-id> --actor agent:<orchestrator-id> --worktree .worktrees/AS-<n> --branch feat/AS-<n>-<slug>` (omit the last two when no branch is cut yet; add `--cycle <k>` on a rework cycle), then `node apps/chat/bin/events.js emit subagent_spawned --task AS-<n> --stage <stage> --employee agent:<employee-id> --actor agent:<orchestrator-id>`. A stage the orchestrator performs itself emits `stage_started` only.
   - **When the employee returns:** `node apps/chat/bin/events.js emit subagent_exited --task AS-<n> --stage <stage> --employee agent:<employee-id> --actor agent:<orchestrator-id> --exit ok|error`.
   - **After the stage's board transition is recorded** (`planned`, `review`, `done`, or a rework transition): `node apps/chat/bin/events.js emit stage_ended --task AS-<n> --stage <stage> --employee agent:<employee-id> --actor agent:<orchestrator-id> --outcome completed|error`.
   If an emit is denied or exits non-zero, write one line in the tick report naming the boundary ("events: emit denied at stage_ended AS-<n>") and carry on — never write the JSONL by hand, never retry inside a compound command, and never emit an event for something that did not happen. A stage left open is closed by the watcher when the tick ends (`cut_by_timeout` on a timeout, `unclosed` on a clean exit), and the count of `unclosed` stages is how the board sees whether this paragraph is being followed. `node apps/chat/bin/events.js open` in step 1 lists what an earlier tick left open, for the same reason `git worktree list` is read there.
4. **Follow the Git Methodology** (see `CLAUDE.md` — revised 2026-08-31, two-plane rule): the MAIN checkout is pinned to master and is the canonical board — ALL `.lattice/` mutations commit to master from there in real time (`AS-<n>: board — <what>`); task branches carry code only, worked inside `.worktrees/AS-<n>/`. Every commit under the employee's git identity (`git -c user.name="<employee-id>" -c user.email="<employee-id>@agents.american-software.local"`). Master is always green for code — app code arrives only via `done` merges. Never check the main checkout out to a task branch. Run `lattice` only from the main checkout (`cd /Users/forrest/Code/american-software-company` first; `git -C <worktree>` for worktree work) — a `cd` into a worktree silently writes board state onto the task branch.
5. **Fulfillment check on `done` (task done ≠ request fulfilled).** When a merge completes a task that *enables* a board request (the description or comments name a deferred act — e.g. "Carla creates the channel once the CLI supports it"), the same tick spawns the owning employee to PERFORM the act and reply to the board. An enabling task closing quietly while the request sits unfulfilled is a failure mode this company has lived once (#bizdev, AS-22) — the merge tick owns closing the loop.
6. **Commit board state per lane, then end the tick clean.** The moment a lane's sub-agent returns, commit that lane's board state to master from the main checkout — the status transition, the Lattice comment, the plan file — before waiting on any other lane (`AS-<n>: board — <what>`, under the orchestrator's git identity). The orchestrator is already the only board writer; this only moves the write earlier, so a tick cut by the timeout loses at most the lane still running and never a finished one (learned 2026-09-11: tick watcher:57637 loop tick 24 finished three lanes and timed out before writing a single transition — two reviews and a plan sat as dirty `.lattice/` until a live session recovered them, 78c8933). Then end the tick clean: statuses truthful, breadcrumbs left, plan/notes files updated, stage work committed on the task branch, master green and pushed if a task merged. The next tick (possibly a different session) must be able to pick up from `.lattice/` state and `lattice branch-link` alone. Remove `apps/chat/data/advance.lock` if this tick created it — releasing the lock is part of ending the tick clean. **The tick report to the board ends with the `needs_human` digest:** one line per open `needs_human` task — code, what is needed, and how many days it has waited — so a board gate cannot sit unnoticed (AS-51 sat ten days). Omit the digest only when the queue is empty, and say so.

## Bounds

- One tick advances each task it touches by at most one lifecycle stage, and touches at most **three** tasks (the WIP limit — board directive #board msg 642, 2026-09-10; see `CLAUDE.md` § Org chart, "WIP limit 3"), each in its own worktree with its own employee, run as parallel lanes from one orchestrator. Or it performs one org-level action. Do not marathon one task through several stages in a single tick, and do not exceed the WIP limit by starting a fourth lane. Lanes are FOREGROUND parallel `Agent` calls in one message (`run_in_background: false`) — background sub-agents are killed 600 s after the orchestrator's turn ends in a headless tick.
- Every stage started in a tick is either ended by its own `stage_ended` emit or closed by the watcher — a tick never deletes or edits a line in `apps/chat/data/events/`.
- **A review's findings become tasks only through the triage gate** (`CLAUDE.md` § Scheduling priority): the reviewer files nothing; the orchestrator files behaviour defects only, at honest priority; test-coverage residuals stay on the parent's record.
- **Board-facing messages are plain language, outcome first** (`CLAUDE.md` § Employees, "Writing to the board"). Any chat message to `human:forrest` leads with what changed or what is needed, carries no test counts, hashes, pids, tick numbers, or internal identifiers (`M4`, `AC-13`, `F1`, red set, floor check), and says no term of art it does not say in words. The evidence goes in the Lattice comment; the message names the task. Glossary: `docs/engineering/04-glossary.md`. Peer channels (`#engineering`, employee DMs) are unaffected. This binds the tick's own report to the board too.
- Approval gates go to the board: EVERY purchase (all spending requires board approval for now — PHILOSOPHY.md #6, threshold removed 2026-08-31), anything touching existing GitHub repos or Digital Ocean services, and genuine judgment calls → `lattice status <task> needs_human` plus a one-line `lattice comment` stating the need, then end the tick. When the ask concerns code on a task branch, open the PR first (PR discipline, step 2) and put its URL in the comment and in the chat message — the board reviews diffs on GitHub, not in Lattice.
- Non-engineering work never gets Lattice tasks (see the Scope section of `CLAUDE.md`).
- If a task hits the 3-review-cycle limit, route it to `needs_human` — never `--force` past it.
- Force-push is always `needs_human`. Never rewrite pushed history autonomously.
- Every in-flight task lives in its own worktree (`.worktrees/AS-<n>/`); the main checkout never leaves master. Task claims and status transitions happen in the main checkout only — one worktree per task, one agent per task per product at a time.
- **This file is the tick's own procedure and the orchestrator may amend it** (`CLAUDE.md` § Operating modes): apply wording a task record has already proposed, commit as `AS-<n>: board — procedure: <what>`. `CLAUDE.md` and the other top-level markdown files stay metawork-only.

## Running continuously

- Message-triggered loop (the normal mode, AS-95): the host watcher (`apps/chat/watch/`) starts a loop of ticks when the board member posts in the chat app, and keeps ticking while anything is mid-lifecycle or a backlog task is ready; it stops when nothing is actionable, on two no-progress ticks, or at the safety cap. Tick timeout 60 min. A loop stopped by the cap with work still mid-lifecycle is a known gap (the self-re-arming cap is a filed watcher task); until it lands, a new board message re-arms.
- `/loop /advance` — self-paced autonomous loop in a live session.
- A single `/advance` — one manual tick, useful for supervised ramp-up.
